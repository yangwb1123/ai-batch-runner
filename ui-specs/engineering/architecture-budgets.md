# Architecture & Complexity Budgets — 模块边界/上帝文件/复杂度治理

核心原则：**让代码因同一个业务原因聚集在一起，让不同业务通过最小稳定
接口协作；任何文件/函数/组件一旦拥有多个独立变化原因，就必须拆分。**

## 1. 依赖方向（单向、可解释）

```
app → pages → widgets → features → entities → shared → 第三方库
```

禁止：shared 引用业务模块；entities 引用 features；features 引用
pages；跨 feature 深层导入内部文件；全局 Store 绕过模块边界。

跨模块访问必须经过公开入口（index.ts 只做导出，不含实现）。

## 2. 按业务能力组织（垂直切片）

推荐 `features/<capability>/` 自包含：`api/`、`model/`、`ui/`、`tests/`、
`index.ts`。禁止按文件类型堆积（components/services/hooks/utils 全局
大杂烩），避免一个订单功能散落十几个目录。

## 3. 上帝文件判定（满足任意 3 项 → 必须拆分）

- 同时负责 UI 渲染、数据请求和业务规则
- 包含 3 个以上独立业务流程
- 管理 5 个以上不同类别的状态
- 包含多个不相关弹窗或表单
- 10 个以上事件处理函数
- 5 个以上 API 调用
- 大量数据转换和映射逻辑
- 被多个业务模块直接依赖
- 无法用一句话描述单一职责

## 4. 复杂度预算（超过不必然错误，但必须标记+说明+补测试）

| 指标 | 建议值 | 超过后 |
|---|---|---|
| 圈复杂度 | ≤ 10 | 评估拆分 |
| 认知复杂度 | ≤ 15 | 必须重构 |
| 函数参数 | ≤ 4 | 参数对象或重新划分职责 |
| 嵌套深度 | ≤ 3 | 守卫语句或拆函数 |
| 函数有效行数 | ≤ 40 | 需说明 |
| 单文件行数 | ≤ 400 | 检查职责 |
| React Hook 数 | ≤ 12 | 检查组件拆分 |
| API 调用数 | ≤ 3/组件 | 检查编排职责 |
| 事件处理函数 | ≤ 8 | 检查是否上帝组件 |
| 单文件导出项 | ≤ 10 | 检查职责过宽 |

优先：守卫语句（嵌套超 3 层）、小型纯函数、策略映射、判别联合、
状态机。禁止：嵌套三元、按 type 参数执行多个不相关流程、any 绕过。

## 5. shared/utils 准入（防垃圾桶）

进入 shared 必须同时满足：≥2 个真实跨业务使用方、无具体业务语义、
API 稳定、不依赖上层。**禁止预判未来复用**——首次出现留在所属模块，
出现第二个真实使用场景再抽象。禁止 `common.ts/helper.ts/util.ts/data.ts`。

## 6. 命名后缀（职责即名字）

`*.api.ts` 请求 / `*.repository.ts` 数据访问 / `*.mapper.ts` 转换 /
`*.policy.ts` 业务规则 / `*.validator.ts` 校验 / `*.machine.ts` 状态机 /
`*.types.ts` 类型 / `*.constants.ts` 常量。禁止 `index2.ts/temp.ts/new-order.ts`。

## 7. 变更影响检查

一个功能修改若需跨越 ≥4 个区域（页面/全局 Store/通用工具/API/基础
组件/路由/权限/类型），应检查架构；正常业务变更应集中在一个 Feature 内。
