# 后端设计智能 03：UI 驱动数据模型（UI-Driven Data Model）

> 不是"数据库有什么字段，页面显示什么"，
> 而是"用户需要什么信息，决定数据结构"。

## 1. 页面需求 → 数据模型推导

页面显示"库存健康度 82% · 预计可生产 35 天 · 风险：缺料 2 项"——

后端不能只有 `inventory_qty`，需要：

| 页面元素 | 所需数据 | 模型决策 |
|---|---|---|
| 健康度 82% | 数量 / 安全库存 | 安全库存字段 |
| 预计可生产 35 天 | 日消耗量 / 供应周期 | 消耗率表 + 供应周期 |
| 风险：缺料 2 项 | 预测缺料日期 | 预测计算（分析服务） |
| 趋势图 | 历史快照 | 时间序列表 |

**规则**：先写页面数据需求清单，再设计表——页面暴露的数据缺口就是模型缺口。

## 2. 派生数据三策略

| 策略 | 适用 | 示例 |
|---|---|---|
| 实时计算 | 低频/小数据 | 健康度 = f(数量, 安全库存) |
| 预聚合（rollup） | 高频读取 | 每日统计表（counter） |
| 物化视图 | 复杂聚合 | 客户上下文（订单+金额+风险） |

**规则**：派生值不裸存（防不一致）；按读取频率选策略；来源表变更时失效/重建。

## 3. 审计与历史是数据模型的一部分

企业系统：价格修改不能 `update price`——

```
Order
OrderVersion（每次变更快照）
ChangeLog（谁/何时/为什么）
ApprovalRecord（审批链）
```

**规则**：业务敏感字段必有版本/历史/审计；审计不可变（append-only）。

## 4. 多租户与未来规模

现在 100 家，未来 10000 家：

- ❌ `company_id` 硬编码在业务逻辑
- ✅ `Tenant / Organization / Permission Model` 显式建模

**规则**：租户边界显式（所有查询带租户条件）；扩展点先于规模到来（克制：不提前造抽象，但边界要正确）。

## 5. 检查清单

```
□ 页面每个数据元素是否有对应模型（含派生所需源数据）？
□ 派生数据是否选对策略（计算/预聚合/物化）？
□ 敏感字段是否有版本/历史/审计？
□ 审计是否 append-only 不可变？
□ 租户/组织边界是否显式建模？
□ 是否有预测/分析类派生（健康度/风险）所需的数据基础？
```
