# 后端设计智能 07：维护智能（Maintenance Intelligence）

> 维护不是"修 Bug"，是持续修正**系统模型与现实世界的偏差**。
> 软件是现实世界的模型（地图≠地形）；现实永远变化，模型不会自动变化。

## 1. 维护的本质

- **模型-现实偏差**：系统的一切腐化都源于此（需求/规模/认知/技术/现实变化）
- **软件熵**：混乱度自发增加（数据重复/代码腐化/权限混乱/文档丢失）——
  维护 = 持续降熵
- **真实性（Trust）**：维护第一目标——系统信息与现实一致（库存 10000
  必须可信）；不可信的系统死亡
- **审计即信任**：谁/何时/改了什么/为什么（append-only，不覆盖）

## 2. 六层维护（不是只有代码）

| 层面 | 目标 | 典型动作 |
|---|---|---|
| 数据 | 真实性 | 清洗、一致性校验、归档、治理（重复/孤儿/失效数据） |
| 业务模型 | 表达现实 | 规则/流程/状态机随现实调整 |
| 用户体验 | 匹配行为 | 交互/流程/效率随用户行为演化 |
| 架构 | 可演化 | 可扩展/可替换/性能（演化架构） |
| 安全 | 抗变化威胁 | 权限/审计/漏洞随攻击方式更新 |
| 知识 | 可接手 | 文档/架构知识/业务知识（新人可接手） |

## 3. 数据维护要点（易错来源 = 人类行为不确定性）

- 人会输错/忘记/误操作/作弊/改变想法 → 数据是"行为痕迹"非事实
- 派生数据三策略防不一致（见 03-ui-driven-data-model）
- 校验规则前置（输入时拦）而不是后置清洗
- 状态变化写历史（ChangeLog），不覆盖
- 定期一致性对账（理论值 vs 实际值差异分析）

## 4. 知识维护（最易忽略）

- 每个模块：现状文档 + 决策记录（ADR）+ 变更日志
- 文档与代码同步（模块文档缺失 = 维护信号）
- 业务知识（为什么这样设计）比技术知识更优先

## 5. 演化设计原则

- 不存在最终系统：诞生→成长→适应→进化→重构（循环）
- 设计是为了未来变化（边界先正确：租户/审计/幂等；抽象克制：三次原则）
- 技术生命周期主动迁移（不等到不可维护）

## 6. Maintenance Agent 职责

系统上线后自动监控并发现：

1. 数据异常（一致性/重复/失效）
2. 性能下降（慢查询/延迟趋势）
3. 代码腐化（复杂度/重复/技术债信号）
4. 用户行为变化（使用率/漏斗/流失）
5. 安全风险（新攻击面/权限漂移）
6. 架构瓶颈（规模逼近设计上限）

每个发现输出：**修复方案 / 优化方案 / 演进方案**（三级，按 ROI 排序）。

## 7. 检查清单

```
□ 系统是否有模型-现实偏差检测（对账/校验）？
□ 数据是否保持真实性（审计/历史/一致性）？
□ 六层维护是否都有责任人/机制？
□ 知识是否维护（文档同步/ADR/业务知识）？
□ 是否主动演化（而非被动修 Bug）？
□ 是否有熵监控（复杂度/技术债/重复信号）？
□ 用户行为变化是否反馈到设计（假设回测）？
```

## 8. 工具映射（ai-batch-runner 已有机制）

| 维护层面 | 工具机制 |
|---|---|
| 数据/代码腐化 | `advance` 自推进引擎（扫描规范维度、状态续跑） |
| 事故沉淀 | `learn`（事故/RCA → Rule Schema → 域注册表） |
| 防回归 | `eval` 规则回归 + 检查器门禁 |
| 知识 | `context` 上下文路由（ADR/契约/安全基线加载） |
| 架构 | `assess`/`rules` 生产就绪评估 |
| 演化 | `campaign` 模块级发现→方向→实现流水线 |
