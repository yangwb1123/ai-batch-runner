# Senior Architecture Constitution — 最高层架构宪法

架构的本质是**管理变化、复杂度、依赖、风险、组织协作与长期成本**。
衡量架构先进性的不是微服务/DDD/事件驱动/模式的数量，而是：
一次需求变化影响多少地方、决策是否可逆、故障爆炸半径多大、
团队是否驾驭得了。

## 1. 变化管理（架构首要目标）

- 识别系统最可能变化的地方、变化频率、必须稳定的部分、长期契约
- 关键指标 **Change Amplification**：一个业务变化需要修改多少模块/
  文件/表/服务/部署单元——目标不是消除变化，而是控制变化传播
- 例：改"客户等级规则"要动 Controller+Service+DB+SQL+缓存+消费者+
  报表+前端 → 变化未被封装

## 2. 决策可逆性

| 决策 | 处理 |
|---|---|
| 易逆转：内部函数名、局部数据结构、模块内目录、非公开接口 | 快速试验 |
| 难逆转：数据库主键、公共 API、事件格式、服务边界、数据所有权、多租户/身份/权限模型、分区策略、外部 SDK、历史数据语义 | 延迟承诺 + 充分论证 |

每个重大决策标记：可逆性（高/中/低）× 迁移成本（低/中/高）×
影响范围（局部/模块/全系统/外部客户）。

## 3. 组织匹配与认知负载（康威定律）

- 系统结构会反映组织沟通结构；4 个团队共维护一个高耦合模块 = 持续冲突；
  3 人团队拆 20 个微服务 = 部署复杂/调试困难/运维失控
- **不要设计一个只有理想团队才能维护的系统**；每个模块/服务/数据有
  明确负责人
- 评估认知负载：完成一个普通需求需理解多少概念？关键行为是否隐藏在
  框架/切面/事件里？是否存在只有少数人懂的"黑魔法"？业务复杂度高时，
  技术架构应降低额外复杂度

## 4. 模块化优先（默认选项，不是微服务）

默认**模块化单体** + 清晰业务边界 + 内部事件 + 独立数据所有权。
拆微服务前必须存在：独立扩缩容/发布需求、团队所有权明确、故障隔离、
技术栈差异、安全边界。顺序：先逻辑边界 → 证明独立部署价值 → 再拆。
**禁止创建分布式单体**（服务多但必须同时发布、共享数据库、同步调用
链长、数据边界不清、一个字段修改全系统发布、本地无法单独运行）。

## 5. 数据所有权唯一

每类核心数据唯一权威所有者，明确：谁创建/修改/校验/发布/修复/
负责生命周期。共享数据库必须有清晰 Schema 所有权与写入权限边界。
**派生数据必须标记**：搜索索引可重建、缓存可丢失、报表可重算、
物化视图可刷新——每类数据说明：是否可重建、从哪里重建、重建期间
如何服务。

## 6. 耦合八型（接口存在 ≠ 低耦合）

代码（直接引用实现）/ 数据（依赖同一表结构）/ 时间（必须同时在线）/
顺序（隐含调用顺序）/ 部署（一起发布）/ 语义（字段隐含含义）/
组织（多团队审批）/ 运行（一个依赖慢拖慢全链路）。审查必须逐型检查。

## 7. 故障隔离与爆炸半径

每个组件定义故障域（单请求/用户/租户/功能/实例/服务/区域/全系统）
和爆炸半径。一个报表任务不得耗尽数据库连接影响下单。用 Bulkhead：
独立连接池/线程池/队列、资源配额、租户限额、超时、熔断、降级。
**不仅要避免失败，还要限制失败传播。**

## 8. 延迟、排队与负载（平均延迟是谎言）

- 关注 P50/P95/P99/P99.9/超时率；长调用链放大尾延迟
- **排队论**：利用率接近饱和 → 延迟急剧恶化 → 超时 → 重试 → 雪崩；
  必须设队列长度/消费速度/拒绝策略/削峰
- **重试是负载放大器**：明确唯一重试责任层、总重试预算、Deadline 传播、
  幂等、抖动、防重试风暴
- **超时预算端到端分配**：总预算 2s → 网关 2s/订单 1.7s/库存 500ms/
  支付 800ms，传播 Deadline 而非每层重新计算
- **背压贯穿**：HTTP/队列/连接池/上传/批处理/日志/搜索——最大队列、
  最大并发、拒绝策略、生产者减速、超载返回码

## 9. 一致性模型显式化

禁止用"最终一致性"代替设计。每类数据明确：强一致/读己之写/单调读/
因果一致/会话一致/最终一致/有界陈旧 + 可接受延迟 + 冲突解决 +
用户可见行为。PACELC：无分区时也要在延迟与一致性间选择。

## 10. 数据重力与读写分离

计算靠近数据（不在应用层拉千万行过滤/跨区域传大对象/应用层重做
数据库聚合）。读路径 ≠ 写路径：规范化写模型 + 面向查询的 Read Model
（订单详情用投影表，不每次 Join 十几张表）。

## 11. 契约演进（Schema 是公共契约，事件是业务事实）

- Schema 变化按 API 管理：版本/兼容/废弃周期/迁移/回填/消费者清单
- 事件：表示业务事实非数据库行变化；已发布语义不可重写；消费者容忍
  未知可选字段；重大变化用新 event_version/event_type
- **废弃是架构能力**：公告/使用统计/迁移指南/双版本周期/截止时间/
  删除门禁——新增版本时同时设计旧版本退出

## 12. 演进式架构与停止条件

- 建立最小可行结构 → 上线观察 → 在保持边界前提下演进；不预先设计
  所有未来能力
- **架构假设清单**：假设/依据/失效条件/监控指标/失效后方案
  （"订单每天不超十万条""状态不会回退""消息严格有序"…）
- **停止条件**：明确目标（500 QPS/P99<500ms/99.9%/日增 100 万行），
  达标后不为幻想的无限规模设计
- 本质复杂度（业务本身）不可避免；**偶然复杂度**（不必要微服务/
  过度抽象/隐式事件链/框架封装）必须避免

## 13. 架构熵治理与投入分级

常见腐化：边界被绕过、临时逻辑变永久、公共工具膨胀、依赖方向破坏、
同一规则多实现。持续治理：依赖规则自动检查、定期审查、清理废弃接口/
Feature Flag/未用依赖、维护架构地图。**热点代码（频繁修改/事故频发/
核心/高并发/安全敏感/数据不可逆）获得更强领域模型/更严测试/更高审查**；
低风险配置页不需要支付系统同级设计。**局部最优可能全局最差**（各自
加重试→重试风暴；各自加缓存→一致性混乱）——从系统整体检查副作用。

## 14. 删除能力与人工干预

- 架构必须支持删除：模块可独立移除、Feature Flag 有清理期限、数据
  可安全迁移、无孤儿数据/隐藏调用方
- 人工恢复必须**设计**而非临时改库：权限控制、双人审批、操作预览、
  幂等执行、审计日志、影响范围、回滚——禁止"找 DBA 手动改表"作为
  正式恢复方案
- 运维/客服/数据/审计人员也是系统的一部分：后台工具、任务重试、
  死信处理、数据修复、状态查询、审计追踪

## 15. 威胁建模与成本

- 用 STRIDE 审查：伪造/篡改/抵赖/泄露/拒绝服务/权限提升——信任边界、
  数据流、不可抵赖需求
- **TCO 而非采购成本**：开发/部署/运维/监控/培训/升级/安全/故障/
  迁移/云资源/供应商——"免费开源"不等于成本低
- 提供基本成本模型：每百万请求、每 GB 存储、日增长、日志保留、峰值、
  灾备

## 16. 架构适应度函数（自动化门禁）

规范不只存在于文档——循环依赖、模块边界、跨层依赖、契约兼容、
Schema/事件兼容、复杂度、性能基线、安全基线、依赖风险必须尽可能
自动化（本仓库的 validators/backendquality 即此类机制）。

## 17. 资深架构师 15 问（方案完成前强制回答）

为什么要这样设计？最可能变化的地方？哪个决策最难逆转？谁拥有这份
数据？谁负责这个模块？一个依赖失败影响谁？最大爆炸半径？达容量上限
如何表现？会否静默产生错误数据？新旧版本能否同时运行？数据如何迁移？
功能将来如何删除？问题发生后谁能看到？如何人工恢复？团队真的能维护？
有没有更简单的方案？
