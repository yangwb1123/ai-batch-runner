# Backend Design Pattern Spec — 按"问题"选模式，禁止为用而用

设计模式不是目标，是解决**已识别**设计问题的工具。Agent 必须先描述
问题、指出变化点，再选模式；没有变化需求时用最简单方案。

## 1. 模式选择决策表

| 问题 | 优先模式 |
|---|---|
| 多种可替换算法 | Strategy |
| 隔离第三方 SDK | Adapter |
| 复杂对象创建 | Factory |
| 复杂系统统一入口 | Facade |
| 隔离持久化 | Repository |
| 多仓储共享事务 | Unit of Work |
| 明确写业务用例 | Command |
| 读写模型差异大 | CQRS |
| 状态转换复杂 | State Machine |
| 规则需要组合 | Specification |
| 多阶段顺序处理 | Chain of Responsibility |
| 横切能力扩展 | Decorator |
| 业务事实触发多个动作 | Domain Event |
| 跨服务长事务 | Saga |
| 数据库与消息一致性 | Outbox |
| 防重复消费 | Inbox / Idempotent Consumer |

## 2. 各模式的使用/禁止条件（摘要）

**Strategy**：✅ 算法可独立变化、≥2 个真实实现、调用方不知算法细节。
❌ 只有一个实现、变化概率极低、只是两三行简单判断。
禁止用 if-else 长链表达可变策略。

**Factory**：✅ 创建逻辑复杂、构造依赖不同。❌ 每个类配一个 Factory、
只有简单 new、为工厂建工厂管理器（DI 容器可替代多数简单 Factory）。

**Adapter**：✅ 隔离支付/邮件/对象存储/消息队列/ERP/数据库驱动等第三方。
关键收益：SDK 字段、异常、升级变化不扩散到业务层。

**Facade**：✅ 隐藏复杂子系统，调用方只知完整业务能力。
❌ Facade 变成上帝类（只负责协调，不承载全部业务规则）。

**Repository**：✅ 表达业务查询。❌ 复制 ORM API 语义。

**Command**：✅ 复杂写操作，输入/边界明确、易测试易审计、可接队列重试权限。
❌ 把所有方法都包装成 Command；简单 CRUD 未必需要。

**CQRS**：✅ 查询维度复杂、读远多于写、写读模型差异大。
❌ 普通 CRUD、小型项目、无明确收益。禁止仅因"高级"引入。

**State Machine**：✅ 订单/审批/支付/工单状态流转。禁止散落
`if (status === ...)` 判断；定义 D→Submitted→Approved→Executing→Completed
及 Rejected 分支，含前置条件/权限/副作用/非法转换。

**Saga**：✅ 跨服务长事务。每步必须幂等、可重试、可补偿、有持久化状态、
超时处理、可人工干预。

**Outbox/Inbox**：✅ 数据库与消息一致性（同事务写 Outbox，后台发布；
消费者用 Inbox/幂等避免重复处理）。事件驱动系统优先考虑。

**Domain Event**：区分同事务强一致逻辑（明确编排）与可异步的最终一致
逻辑；禁止把核心业务规则藏在 Observer 里。

## 3. 过度设计红线（硬性禁止）

- 每个类都创建接口；每个对象都通过 Factory 创建
- 只有一个实现且无明确变化需求时创建多层抽象
- 普通 CRUD 强制套 DDD、CQRS、事件溯源
- 创建 BaseService/BaseManager/BaseController/BaseEntity 承载通用逻辑
- 为未知未来需求预留扩展点；抽象名称无法表达业务含义
- 接口与实现一一对应但没有替换、隔离或测试价值
- 多层 Decorator 嵌套导致调用链不可理解

## 4. 三次原则

1. 第一次：实现具体代码
2. 第二次：允许有限重复
3. 第三次：确认稳定共性后再抽象

涉及明确架构边界、安全边界、外部依赖隔离时不受此限。

## 5. 每次引入模式必须说明

当前存在什么问题 / 变化点是什么 / 为什么简单函数或组合不足 /
模式解决了什么 / 增加了什么复杂度 / 如何测试该模式。
