# Backend Complexity & Scale Spec — 复杂度分析与数据规模推理

## 1. 五类成本（不只 CPU）

| 成本 | 分析点 |
|---|---|
| CPU | 时间复杂度 O(1)/O(log n)/O(n)/O(n log n)/O(n²) |
| 内存 | 一次加载 500 万行，即使 O(n) 也可能 OOM；对象 vs 位图 |
| 数据库 | 扫描行数、索引命中、回表、排序、临时表、锁、事务时长、往返次数 |
| 网络 | 批量 vs 循环远程调用；RTT、payload、序列化、超时、并发、限流 |
| 分布式协调 | 分布式锁、共识、跨服务事务、重试、消息重复、时钟偏差、分区 |

循环查库/远程调用的真实成本常比纯算法复杂度更严重（N+1）。

## 2. 避免清单（机械可查）

- 循环内 `.find/.includes/.filter` 的嵌套查找（O(n²) 信号）
- 循环内 `await` 数据库/远程调用（N+1：用批量 + JOIN + Promise.all）
- `array.shift()` 当队列（O(n)，用 Deque/head 指针）
- 全量排序后取 Top K（用堆：O(n log k)）
- 一次加载全部大数据；无界递归/队列/缓存/并发

## 3. 数据规模推理（每次实现必须回答）

| n | 内存 | DB I/O | 网络往返 |
|---|---|---|---|
| 1 万 | 数组/Map 随意 | 索引即可 | 单次批量 |
| 100 万 | 注意对象开销 → 位图/紧凑结构 | 需要覆盖索引/分页 | 分页/游标 |
| 1 亿 | 常驻内存不可行 → 流式/外部存储 | 分区/汇总表/OLAP | 只查必要字段 |

×10/×100 后当前选型是否仍成立？不成立时替换方案是什么？
（例如 Bloom Filter 预过滤、Bitmap 计数、倒排索引、一致性哈希分片）

## 4. 优化顺序

保证正确性 → 确认数据规模与性能目标 → 日志/指标/Profiling 找瓶颈 →
优化算法与数据结构 → 减少 DB/网络 I/O → 批处理与并发池 → 必要时
缓存/索引/预计算 → 基准测试验证。

不得为理论复杂度降低而显著增加系统复杂性，除非数据规模和性能测试
证明有必要。未经基准测试不得声称性能已优化。

## 5. 算法交付要求（非平凡算法/数据结构）

为什么选它 / 为什么不选其他方案 / 时间复杂度 / 空间复杂度 /
数据规模假设 / 边界条件 / 并发影响 / 失败模式 / 基准测试方法 /
何时需要替换方案。
