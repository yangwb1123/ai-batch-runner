# Backend Evolution Spec — 工程演进规范（防止架构腐化）

## 1. 重构触发条件（命中 → 先重构再声明完成）

- 文件持续增长且无清晰边界（>400 行）
- 修改一个简单需求需同时改动 ≥4 个不相关区域
- 一个 Service 被 ≥10 个模块直接依赖
- 同类业务规则在 ≥3 处重复（第三次原则到期）
- 出现跨模块内部路径引用 / 循环依赖
- 状态判断散落多处，改动一处遗漏他处

拆分维度优先级：业务能力 > 用例 > 变化原因 > 生命周期 > 数据一致性
边界 > 技术实现。禁止机械拆分（order-helper-1.ts / order-common.ts）。

## 2. 变更分级与渐进迁移

区分：新功能 / 局部重构 / 架构迁移 / 破坏性变更。

| 场景 | 手段 |
|---|---|
| 大改造 | Adapter / Facade / Feature Flag / 双写双读 / 逐模块迁移 |
| 接口升级 | 兼容窗口（旧接口 Deprecation 标记，不立即删除） |
| Bug 修复 | 修复根因 > 补充边界保护 > 局部兼容 > 临时规避 > 关闭规则 |
| 依赖升级 | 锁文件提交、CI 固定版本、升级后全量门禁 |

禁止：修一个 Bug 时顺手重写整个模块；为"重构干净"一次改动全项目。

## 3. ADR 决策记录

重要工程决策（为何用 Feature 模块划分、为何不用全局 Store、为何统一
Repository、为何禁用某模式）必须记录：`docs/adr/NNNN-title.md`——
背景、决策、备选方案、后果。Agent 遇到已有 ADR 必须遵循，除非明确
发起架构变更。

## 4. 技术债登记（禁止大量裸 TODO）

```yaml
debt:
  title: 订单列表仍使用旧请求层
  risk: medium
  reason: 本次任务不适合全量迁移
  follow_up: 迁移到统一 repository
  owner: order-team
```

每个 TODO 必须有原因/Owner/日期/跟踪编号/触发条件。

## 5. 可演进性检查

- 更换实现（Prisma→TypeORM、Stripe→PayPal、SQL→Mongo）是否只需改
  Infrastructure 层
- 第三方 SDK 字段/异常/升级是否被 Adapter 隔离
- 新增一种策略/渠道/格式是否需要修改核心业务代码
- 向后兼容：数据结构变更是否前后兼容；发布与回滚是否可行（唯一版本号、
  静态资源哈希、HTML 不长期缓存）
- 多环境配置统一校验（env schema），密钥不进前端/不进日志

## 6. 架构审查清单（完成前必查）

1. 模块是否有清晰业务边界
2. 依赖方向是否单向、有无循环依赖
3. 核心业务是否依赖框架/ORM/SDK
4. 是否存在上帝类/上帝文件
5. 是否访问其他模块内部实现
6. DTO/领域/ORM 实体是否混用
7. 是否存在单实现无意义的接口（过度抽象）
8. 是否用大量 switch/if 表达可变策略
9. 状态转换是否分散
10. 横切逻辑是否复制到多模块
11. 第三方 SDK 是否被 Adapter 隔离
12. 事务边界是否在用例层
13. 模块能否独立测试
14. 修改一种实现是否需要改大量调用方
15. 是否引入模式但未说明问题/变化点/复杂度/测试
