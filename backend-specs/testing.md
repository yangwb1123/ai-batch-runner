# Backend Testing Spec — 测试工程（五层策略 + 复现优先 + 防伪造）

## 1. 五层测试（不是只写单元测试）

| 层 | 覆盖 | 关键点 |
|---|---|---|
| 单元 | 领域规则、纯函数、算法 | 不连 DB/网络 |
| 集成 | DB、缓存、消息、外部适配器 | 用真实/嵌入式依赖或契约替身 |
| 契约 | API/消息兼容性 | 消费者契约测试，防破坏旧客户端 |
| E2E | 完整用户流程 | 少量关键链路 |
| 非功能 | 性能/安全/并发/故障恢复 | 基准、竞态、混沌 |

## 2. Bug 修复流程（强制）

1. **先写能复现 Bug 的测试** → 确认测试失败（复现）
2. 修复代码 → 测试通过
3. 回归相关模块

禁止：先改代码再"补"测试；跳过复现直接猜修。

## 3. 覆盖风险，不追数字

- 覆盖率是工具不是目标；必须测的高风险路径：异步乱序、重复提交、
  超时 uncertain、409 冲突、权限变化、组件/服务卸载、乐观更新回滚、
  分页边界、时区/精度边界、多人编辑、部分成功
- 禁止只测"能渲染/按钮存在"不测业务结果
- 修复 Bug 时测试必须能证明"这个缺陷不会再回来"

## 4. 属性测试与模糊测试

- 金额分摊：所有分项之和 = 总额、每项 ≥ 0、相同输入结果稳定——适合
  Property-based Testing
- Parser/文件处理/协议解析/URL/JSON 转换/加密边界/用户输入——适合
  Fuzz Testing

## 5. 测试数据治理

- 用 factories/fixtures/scenarios 表达业务场景（正常订单/超期订单/
  已锁定订单/权限不足订单/409 冲突订单），禁止复制完整大对象
- 测试数据表达场景语义，不表达随机值

## 6. 禁止事项

- 把失败测试标记为 skip 来让流水线通过
- 为通过测试修改测试预期
- 只测正常路径；无断言的测试文件
- 测试里 `sleep` 硬等（用可控时钟/等待真实条件）
- 伪造测试结果（"理论上应该通过"）
- 测试依赖执行顺序/共享可变状态

## 7. 集成测试隔离

- 每个测试独立数据库/缓存（事务回滚或每测试重建）
- 外部依赖用可控替身（延迟注入：能控制响应顺序/超时/失败）
- 竞态测试用两个 Deferred Promise 控制返回顺序
