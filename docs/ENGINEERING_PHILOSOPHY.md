# 软件工程哲学总纲（Engineering Philosophy）

> 体系最高指导思想。所有规范、门禁、角色都服务于这个第一性理解：
> **软件是人类认知能力的外化，是现实世界的模型；维护是持续修正模型
> 与现实之间的偏差；AI 时代的核心不是写更多代码，而是把人类从重复
> 劳动中解放，让人做判断与创造。**

## 一、软件的本质：认知外化

- 代码只是表现形式。软件的本质是：把人的**意图、知识、规则、经验、
  判断过程**固化为可重复执行的系统。
- 人类智慧（经验→判断→行动）→ 软件（规则→算法→执行）：**智慧的复制、
  放大与自动化**。
- 会计不是被 ERP 替代，而是财务知识变成了机器可执行的流程。

## 二、一次软件调用 = SmartFunction

一次操作（"生成报表"）不是简单函数调用，而是：

```
SmartFunction(UserContext, BusinessContext, HistoricalData, Goal)
```

包含：上下文、权限、历史、规则、推理。设计接口时按此签名思考——
端点缺上下文聚合就是认知缺失（见 design-intelligence/01-experience-driven-api）。

## 三、人类现实世界缺什么（软件的第一性需求）

| 缺口 | 软件提供 | 例 |
|---|---|---|
| 记忆有限 | 外部记忆 | 文档→数据库→知识库→AI |
| 计算有限 | 大规模计算 | 百万订单风险预测 |
| 协作困难 | 协作规则 | Git、ERP |
| 不一致 | 稳定执行 | 银行利息不随心情 |
| 不可见 | 可观察性 | 机器效率/异常/趋势可视化 |
| 重复劳动 | 自动化 | 把重复行为交给机器 |

**设计检查**：这个页面/功能填补了哪个人类缺口？如果没有明确答案，
可能是伪需求。

## 四、系统维护的本质（为什么维护）

### 4.1 系统是现实世界的模型

软件 ≈ 地图，现实 ≈ 地形。**地图 ≠ 地形**。

现实永远变化（多币种/跨境/ESG/AI 报价），模型不会自动变化——维护就是
持续修正**模型与现实之间的偏差**。

### 4.2 软件熵（Software Entropy）

系统运行中混乱度自发增加：数据重复、代码腐化、权限混乱、文档丢失、
性能下降。维护 = **持续降低熵**（如同整理房间）。

### 4.3 数据为什么容易出错

数据库的数字只是"人类行为留下的痕迹"——人会输错、忘记、误操作、
作弊、改变想法。`库存 = 入库 - 出库` 在现实中总有偏差（少扫描/多录/
退货未处理/人工调整）。

**维护第一目标：保持系统真实性（Trust）**。老板看到库存 10000 必须能
相信现实接近 10000——不可信的系统死亡。

### 4.4 为什么需要审计

人会犯错 → 需要知道谁/何时/改了什么/为什么（订单 100万→80万，
修改人张三/时间/原因：客户折扣）。没有审计 = 系统失去可信。

## 五、系统为什么必须演化（五个变化源）

1. **需求变化**：软件最大的敌人不是 Bug 是 Change（微信：聊天→支付→小程序）
2. **规模变化**：100 用户单体 → 100 万用户分布式
3. **认知变化**：菜单时代 → 搜索/AI 时代（"告诉我为什么这个订单延期"）
4. **技术生命周期**：Flash→Web、PHP5→PHP8、单体→云原生
5. **现实变化**：业务规则/流程/状态随现实调整

**设计原则：设计系统不是为了今天运行，而是为了未来变化。**

## 六、成熟系统维护六个层面

| 层面 | 目标 | 内容 |
|---|---|---|
| 数据维护 | 真实性 | 清洗/一致性/归档/治理 |
| 业务模型维护 | 表达现实 | 规则/流程/状态调整 |
| 用户体验维护 | 匹配行为 | 页面/流程/效率优化 |
| 架构维护 | 可演化 | 可扩展/可替换/性能 |
| 安全维护 | 抗变化威胁 | 权限/审计/漏洞 |
| 知识维护 | 可接手 | 文档/架构知识/业务知识 |

## 七、演化设计（软件生命体）

不存在最终系统——只有不断适应环境的系统（如生物）：

```
诞生 → 成长 → 适应 → 进化 → 重构（循环）
```

## 八、AI 时代的软件定位

### 8.1 传统 vs AI 时代

```
以前：人 → 规则 → 软件 → 执行（人适应软件）
未来：人 → 目标 → AI 理解 → 生成规则 → 软件执行（软件理解人）
```

### 8.2 AI Coding 的真正意义

不是"写代码更快"，而是**降低创造软件的门槛**——领域专家描述问题，
AI 构建工具（一个人 = 产品经理+UI+前端+后端+运维）。

### 8.3 优秀 Prompt 的本质 = 产品需求

❌ "帮我写一个商城"（功能）
✅ "小工厂排产有问题：计划员每天 4 小时调订单。目标 30 分钟。
用户是 PMC。约束：不改变现有 ERP。请设计智能排产助手。"（产品需求）

### 8.4 AI Agent 补充人类的四件事

1. 人类缺少耐心的事（持续执行：数据整理）
2. 人类容易遗漏的事（检查：代码审查/安全扫描）
3. 人类无法同时处理的信息量（分析：百万订单风险）
4. 人类没有时间学习的知识（知识调用：法律/医学/工程）

### 8.5 未来软件不是 App 而是 Agent

```
传统：用户点击按钮/菜单/页面
未来：用户表达"我要降低库存成本 20%" → Agent 理解（当前库存/销售预测/
      供应周期/供应商）→ 自动行动
```

## 九、Problem Solving Intelligence（Agent 能力模型）

Problem Understanding

## 十、最终哲学

软件存在的意义：**帮助人类把有限的生命从重复、机械、低价值劳动中
释放出来，把更多时间用于创造、探索、判断和体验。**

好软件不是功能多，而是：理解人的目的、降低认知负担、放大能力、
减少错误、帮助做更好的决定。

AI Coding 时代真正的问题：**人类还有哪些痛点、低效、重复、复杂、
不确定的问题，可以被重新抽象成智能系统？**

## 十一、分发的本质（Distribution as Propagation）

### 11.1 为什么软件必须传播

价值需要从局部变成普遍。一个算法只服务 1 人 vs 服务 10000 家工厂——
软件是可复制的信息结构（copy() 零边际成本），这是它区别于物理商品的
根本（复制一座工厂需要土地/设备/人员）。

**没有分发的软件只是某台电脑里的代码，没有进入人类系统。**

### 11.2 跨学科视角

| 学科 | 视角 |
|---|---|
| 物理学 | 光传播能量改变物质世界；软件传播"信息能量"改变组织运行 |
| 信息论 | 软件降低不确定性（老板猜测 → 系统显示 82% 产能利用率）；传播 = 传播降低不确定性的能力 |
| 控制论 | 软件传播控制能力（感知→判断→行动；仪表之于飞机） |
| 生物学 | 软件是"数字基因"：设计思想/工程经验跨代传播（Git 传播版本管理思想、Docker 传播容器化思想） |
| 哲学 | 传播是信息结构从"存在"走向"产生影响"的过程——知识成为可执行形式 |

### 11.3 分发是产品设计的一部分（不是最后才考虑）

- 微信设计传播机制：一人使用 → 邀请 → 网络效应
- GitHub：代码 → Star → Fork → 贡献者 → 社区

**设计检查**：产品是否设计了传播路径（邀请/分享/网络效应/生态）？

### 11.4 AI 时代：软件从"产品"变成"能力"

```
以前：开发公司 → 应用商店 → 用户安装
未来：问题出现 → 用户描述 → Agent 生成工具 → 立即使用 → 分享
```

**最大机会**：创造软件成本趋零后，问题不再是"怎么写"，而是
**"什么问题值得被软件化"**——寻找：重复劳动/信息不对称/经验无法复制/
决策困难/协作困难。

## 十二、进化闭环（Agent 自我迭代的本质）

### 12.1 从函数到控制闭环

```
传统函数：input → 固定规则 → output（开环）
Agent：Goal → Observe → Reason → Act → Feedback → Update（闭环）
```

### 12.2 体现的核心观点

- **控制论**：智能来自反馈（恒温器模式；测试失败 → 分析 → 调整 → 重生成）
- **PDCA**：Plan → Do → Check → Act（企业管理与 Agent 同构）
- **经验资产化**：优秀工程师离职经验消失 vs Agent 把经验变成规则+案例+失败记录（Engineering Memory）
- **认知科学**：错误 → 反思 → 调整（成长来自错误而非一直成功）
- **进化论**：变异 + 选择（多方案生成 → 测试 → 保留最佳）

### 12.3 学习数据分层（不是所有日志都有价值）

| 层 | 内容 | 价值 |
|---|---|---|
| Observation | 发生了什么（输入/决策/结果/耗时） | 记忆 |
| Outcome | 成功还是失败 | 评价 |
| Reasoning | **根因**（违反什么原则） | 最关键 |
| Knowledge | 抽象成规则（100 个 bug → 80% 边界遗漏 → 规则） | 预防 |

### 12.4 Error → Rule Pipeline（必须闭环）

```
Bug → Root Cause → Pattern → Rule → Validation → 加入规范 → 未来预防
```

**禁止**：Bug → 修复 → 结束。

### 12.5 Reflection（复盘机制）

每个任务结束执行 Post-Task Review：目标是否完成 / 用户真正需求 /
成功 / 失败 / 根因 / 下一次避免 / 新增规则。

### 12.6 Agent Governance（治理：防止乱进化）

| 等级 | 规则 | 示例 |
|---|---|---|
| L0 不可违反 | 安全/权限/数据保护 | fail closed |
| L1 工程规范 | 架构/代码质量 | 门禁 |
| L2 优化建议 | 性能/体验 | 建议 |
| L3 实验性 | 策略探索 | A/B |

### 12.7 完整进化循环

```
问题 → 设计 → 实现 → 运行 → 数据反馈 → Agent 观察 → 经验积累
→ 策略优化 → 软件进化 → 再次服务人类
```

软件从"一本书"（写完固定）变成"生物"（感知环境、调整行为、积累经验）——
具备部分生命系统特征（人工生命系统思想）。

## 十三、问题系统分类学（哥德尔启发）

哥德尔不完备定理的本质启发：**没有一个系统能解决所有问题——每个形式
系统都有自己的完备性边界**。因此软件工程的第一步不是写代码，而是
**判定问题属于哪类系统**，再选择该类系统的方法论。

### 13.1 判定 → 方法论路由

| 问题系统类型 | 特征信号 | 方法论 |
|---|---|---|
| 确定性业务系统 | 规则明确、事务边界清晰 | 事务 + 约束 + 状态机 |
| 状态机系统 | 状态流转、非法转换 | 集中状态机 + 事件 + 历史 |
| 事件系统 | 跨服务流转、异步 | 事件驱动 + 幂等 + 最终一致 |
| 流系统 | 数据持续产生、背压 | 队列 + 背压 + 批处理 |
| 优化系统 | 约束 + 目标函数 | 建模 + 求解（线性/启发式） |
| 搜索系统 | 海量 + 相关性 | 索引 + 排序 + 缓存 |
| 知识系统 | 经验/文档/不确定回答 | RAG / 知识图谱 / 检索 |
| 协作系统 | 多人/多角色 | 工作流 + 权限 + 通知 |
| 不确定决策系统 | 预测/风险评估 | 统计模型 + 置信度 + 人机协同 |
| 智能自适应系统 | 环境变化、目标驱动 | Agent 闭环 + 学习 |

### 13.2 判定方法（Prompt 分类学）

1. 读 prompt 的**意图动词**（查询/流转/预测/优化/协作/生成）
2. 找**系统特征**（状态/事件/并发/规模/不确定/多角色）
3. 归入一类主系统 + 若干子系统
4. 主系统决定方法论骨架，子系统决定补充模式

### 13.3 应用（AI Coding）

- `classifier`：前端/后端任务路由（已有）
- `rule_matcher`：三轴规则筛选（已有）
- **本分类学**：系统类型 → 方法论文件路由（新增维度）
- 哥德尔的教训：**不承认系统边界 = 用错误方法论硬套**（如用 CRUD 套事件系统）
