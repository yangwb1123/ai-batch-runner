# Product Discovery — 管理员删除文件：通知所有者 + 审计

> 输入：`requirements/current.md`（原始需求原文，未改动）。
> 本文件只做目标解释与范围界定，**不设计 API、不修改代码**；
> 具体协议/事件/落账方式留给后续组合与变更设计阶段。

## Interpreted Goal

原始需求的字面操作链是「管理员删除文件 → 通知所有者 → 记录审计」，但真正的
用户目标是**管理删除的透明性与可问责性**，删除操作只是触发点：

1. **所有者知情**：当管理员以治理身份删除了某个用户的文件，该用户必须明确
   知道「我的文件被删了、是谁删的、为什么删」——删除不是悄悄消失，也不能让
   用户误以为是自己误删或系统故障。
2. **可问责记录**：删除动作留下不可抵赖、可查询、可导出的记录，供事后追责、
   安全调查与合规审计使用（谁、何时、哪个文件、结果如何）。

平台背景（6 个独立产品组合）意味着：通知能力属于 aero-im、文件事实属于
aero-vault、审计事实源是 snaplink-audit-governance、管理操作入口在
snaplink-console、操作者身份由 snaplink 判定——但这是组合层面的约束，不是本
需求的产物；本阶段只确认「知情 + 可问责」两个目标成立。

**刻意不做（防止膨胀）**：不做回收站/恢复流程、不做批量删除、不做审批流、
不重新设计文件删除权限模型、不要求通知送达的强制确认。

## User Roles

| 角色 | 定位 | 关注点 |
|---|---|---|
| 管理员（发起者） | 在 snaplink-console 操作删除；身份与权限由 snaplink 判定 | 删除是治理动作，需要表达原因，知道自己做的事有据可查 |
| 文件所有者（受影响者） | 被删文件归属的普通用户（aero-id 账户） | 知道文件没了、为什么没了、找谁申诉 |
| 审计/合规查询者（查询方） | 安全、合规、客服人员；读取 audit-governance 账本 | 完整、不可篡改、可检索的删除事件记录 |
| 审批者 | **需求中不存在** | 需求未提审批；默认无审批环节（见 P2/P3 演进项） |

## Scope Priority

默认实现覆盖 **P0 + 明确必要的 P1**；P2/P3 仅记录为演进方向，不进入默认范围。

### P0（必须）

- 管理员经管理端删除文件（删除对象明确：哪个文件、属于谁、何时）。
- 删除后文件从所有者的可见列表中消失——删除语义成立，文件不再可访问。
- 所有者收到通知（经 aero-im 渠道），内容至少包含：哪个文件、被删除。
- 删除事件写入 snaplink-audit-governance 统一审计账本：操作者、时间、文件、
  所有者、结果，作为全平台唯一事实源。

### P1（强烈建议，默认包含）

- **删除原因**：管理员删除时提供原因，随通知与审计记录一并呈现。无原因的
  「已删除」通知对所有者近乎无用，无原因的审计记录对合规近乎无用——这是让
  P0 两个目标真正成立的最小补充。
- **所有者可查询删除记录**：即使通知送达失败，所有者也能在「我的文件/通知
  历史」中查到删除事件。通知是尽力而为的渠道，账本才是事实源。
- **审计事件关联标识**：file id、owner uid、管理员身份（含管理端会话上下文）
  齐备，保证可追溯、可串联。

### P2（增强，不在默认范围）

- 通知失败的重试与第二渠道（如邮件）升级。
- 管理端删除历史浏览页（console 侧查询）。
- 批量删除的聚合通知。
- 软删除/回收站与恢复流程（若产品路线需要，属独立需求）。

### P3（未来，仅记录）

- 不可逆删除的双人复核（two-person rule）。
- 与 Legal Hold 的交互（被保留文件不可删）。
- 所有者已读回执/申诉闭环。

## 对技术假设的保留

需求的字面表述暗示「删除 → 通知 → 审计」的线性流程，但本发现层**不预设**：
通知是同步还是异步、审计由哪个组件负责落账、删除是硬删还是先软删、通知失败
是否阻断删除——这些留给组合与变更设计阶段按各产品能力裁决，本文件只确立
「所有者知情 + 可问责记录」两个目标与上述范围。
