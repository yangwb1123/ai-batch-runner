## Scope and Current Evidence

**Scope — Proposed**

- First slice is the existing `sverpweb-stable` purchase approval path: create draft → submit → one human approval → approve or reject.
- Runtime is the current Bun SQLite deployment with one configured tenant and one database. `tenant_id` is a server-side boundary marker, not a shared-instance multi-tenancy feature.
- Workflow facts remain in `sverpweb-stable` module-local SQLite tables. No new workflow Git repository, service, or shared database is created.
- `execute`, `fail`, `compensate`, and `recover` command ports are reserved but not enabled in this approval-only slice; no purchase side effect is executed.

**Verified**

- `purchase-requests.ts` uses `bun:sqlite`, creates `purchase_requests`, and generates UUID text IDs with `randomUUID()`.
- The supplied current purchase columns are:

  `id`, `item_code`, `qty`, `requester`, `approver`, `approver_position`, `status`, `reason`, `created_at`, `resolved_at`, `updated_by`, `deleted_by`, `deleted_at`.

- Current status constraint is exactly:

  `draft`, `pending_approval`, `approved`, `rejected`.
- Current indexes are `(approver, status, created_at)` and `(requester, status, created_at)`.
- Current reads use `SELECT *`; list queries use `LIMIT 50`.
- Current status writes do not use an aggregate version or state-history table.
- The route mutates purchase state before calling `emitAuditEvent`; notification writes are also after the business mutation.
- `platform-map.yaml` assigns purchase and first-slice workflow ownership to `sverpweb-stable` and forbids direct cross-project database access.

**Transitional**

- Schema creation and `ALTER TABLE` operations occur inside `PurchaseRequestStore` construction rather than a versioned migration process.
- `approver` and `approver_position` are compatibility fields. Workflow candidates become the authoritative approval snapshot after cutover.
- `emitAuditEvent` is not demonstrated to be atomically coupled to the purchase mutation. The supplied gate explicitly says the audit target is not yet connected to governance.

**Missing**

- The actual SQLite database path, current row counts, existing migration mechanism, backup procedure, and deployed schema fingerprint.
- Server-side tenant-context extraction from the current auth session.
- The authoritative `aero-id` department/membership contract.
- The active audit-governance ingest endpoint, required `EventEnvelope` fields, schema version, and receipt semantics.
- Existing workflow persistence tables, if any, were not supplied as evidence.
- Quantity semantics: integer quantity, decimal quantity, unit, scale, and allowed range are unknown.
- Business retention, legal hold, and privacy-erasure policy are unknown.

## Persistence Models

**Model separation — Proposed**

| Model | First-slice responsibility |
|---|---|
| API DTO | `itemCode`, `qty`, optional approver selector, reason, idempotency header; never accepts authoritative tenant or actor |
| Domain model | `PurchaseRequest`, `WorkflowInstance`, `WorkItem`, approval rules, transition validation, invariants |
| Persistence model | SQLite rows, keys, indexes, JSON serialization, migration compatibility |
| Read model | Explicit projections for requester lists, pending approvals, detail, and history; never returns ORM/database rows directly |

Storage conventions:

- IDs and enum values use SQLite `TEXT`.
- Timestamps use `INTEGER` UTC Unix milliseconds, generated by the server.
- Versions and counts use `INTEGER`, starting at `1` for aggregate versions and `0` for retry counts.
- JSON is `TEXT` only for bounded snapshots or immutable definitions; it is not used for queryable relationships.
- Application byte limits are required in addition to SQLite `length()` checks.

## Aggregate and Transaction Boundaries

**Aggregate ownership — Proposed**

- `PurchaseRequest` owns `purchase_requests` and `purchase_request_status_history`.
- `WorkflowInstance` owns workflow definition references, work items, candidates, approval decisions, and workflow history.
- `audit_outbox` is an integration buffer, not an aggregate and not a business source of truth.
- A workflow instance references a purchase aggregate by typed ID; it does not own purchase fields.

The workflow module has no SQL access to `purchase_requests`. It calls this typed port:

```text
PurchaseAggregateCommandPort
  create(ctx, command)
  submit(ctx, purchaseId, expectedPurchaseVersion, idempotencyKey)
  approve(ctx, purchaseId, expectedPurchaseVersion, reason, idempotencyKey)
  reject(ctx, purchaseId, expectedPurchaseVersion, reason, idempotencyKey)
  return(ctx, purchaseId, expectedPurchaseVersion, reason, idempotencyKey)
  cancel(ctx, purchaseId, expectedPurchaseVersion, reason, idempotencyKey)
  execute(ctx, purchaseId, expectedPurchaseVersion, idempotencyKey)
  fail(ctx, purchaseId, expectedPurchaseVersion, errorCode, idempotencyKey)
  compensate(ctx, purchaseId, expectedPurchaseVersion, command, idempotencyKey)
  recover(ctx, purchaseId, expectedPurchaseVersion, recoveryCommand, idempotencyKey)
```

Only `create`, `submit`, `approve`, and `reject` are enabled in the first slice. Disabled commands return a typed `command_not_enabled` result without writing any table.

A single local unit of work coordinates owned tables. The workflow service may write workflow tables through its persistence adapter, while the purchase port is the only component that issues purchase-table writes.

**Create transaction**

```text
BEGIN IMMEDIATE

validate server-derived context and required idempotency key
insert operation_idempotency(purchase.create)
if duplicate:
    compare request_digest
    replay prior resource/version or return idempotency_conflict

purchase module:
    insert purchase_requests(status='draft', version=1)
    insert purchase_request_status_history(NULL -> draft, version=1)

insert audit_outbox(purchase_request.created.v1)
mark operation_idempotency succeeded

COMMIT
```

Failure of any insert rolls back the purchase row, history, idempotency record, and outbox row together.

**Submit transaction**

```text
BEGIN IMMEDIATE

check/replay operation_idempotency(workflow.submit)
load purchase through PurchaseAggregateCommandPort
purchase port:
    verify tenant, requester authority, status='draft', expected version
    UPDATE purchase_requests
      SET status='pending_approval',
          submitted_at=?,
          updated_at=?,
          updated_by=?,
          version=version+1
      WHERE tenant_id=? AND id=? AND status='draft' AND version=?
    require changes == 1
    insert purchase status history
    return new purchase version

workflow module:
    insert workflow_instances(definition_id/version, status='waiting')
    insert workflow_work_items(status='pending')
    insert workflow_work_item_candidates
    insert workflow_instance_history
    insert audit_outbox(workflow.submitted.v1)

mark idempotency succeeded with both resource references

COMMIT
```

If workflow creation fails, the purchase submission is rolled back. The workflow module never updates `purchase_requests` itself.

**Approve/reject transaction**

```text
BEGIN IMMEDIATE

check/replay operation_idempotency(workflow.approve or workflow.reject)
load workflow instance and work item using tenant-scoped keys
verify workflow/work-item expected versions and pending state
recheck current authorization, applicant separation, delegation, and grant status

call PurchaseAggregateCommandPort.approve(...) or reject(...)
    the port verifies purchase tenant, status, and expected purchase version
    the port updates purchase row and purchase history only

insert immutable workflow_approval_decisions
update workflow_work_items with expected claim/version checks
update workflow_instances with expected current_version check
insert workflow and work-item history
insert audit_outbox for purchase and workflow facts
mark idempotency succeeded

COMMIT
```

No HTTP call to audit-governance, notification, organization, or another service occurs inside the SQLite transaction. Such calls happen after commit through a durable adapter or explicitly best-effort integration.

For future execution, the transaction boundary ends before the external side effect. The system first commits an execution record, then performs the side effect, then calls the purchase aggregate command port with the recorded execution idempotency key. Deployment rollback cannot undo that side effect; compensation is a separate business command.

## State History and Optimistic Concurrency

**Purchase state machine — Proposed**

| Code | State | Allowed transition |
|---:|---|---|
| 10 | `draft` | create |
| 20 | `pending_approval` | `draft → pending_approval` |
| 30 | `approved` | `pending_approval → approved` |
| 90 | `rejected` | `pending_approval → rejected` |

The string values preserve the current API contract. Numeric codes are domain constants and are never reused. There is no direct `draft → approved`, `approved → completed`, or `rejected → approved` transition in the first slice.

**Workflow state machine — Proposed**

- Creation plus deterministic routing produces `waiting`.
- `waiting → approved` occurs after a valid approval decision.
- `waiting → rejected` occurs after a valid rejection decision.
- `return`, `cancel`, `expired`, execution, and compensation states are contract-defined but disabled in this slice.

Every accepted state or aggregate mutation:

1. Loads the current version.
2. Validates the centralized transition table.
3. Performs an expected-version update.
4. Inserts exactly one history row for the new version.
5. Emits an audit outbox event in the same transaction.

Representative purchase update:

```sql
UPDATE purchase_requests
SET status = ?,
    reason = ?,
    resolved_at = ?,
    updated_at = ?,
    updated_by = ?,
    version = version + 1
WHERE tenant_id = ?
  AND id = ?
  AND status = 'pending_approval'
  AND version = ?
  AND deleted_at IS NULL;
```

`changes == 0` is not treated as success. The service distinguishes not-found/tenant mismatch from `version_conflict` by a tenant-scoped reread. It never overwrites a newer version.

Workflow and work-item updates use the same pattern:

```sql
UPDATE workflow_instances
SET status = ?,
    current_version = current_version + 1,
    updated_at = ?
WHERE tenant_id = ?
  AND workflow_instance_id = ?
  AND status = ?
  AND current_version = ?;
```

Concurrent approve/reject behavior:

- Exactly one command can update the purchase and workflow versions.
- The losing command receives a structured conflict or invalid-state error.
- Only one approval decision, history chain, and corresponding business transition is committed.
- A retry must use the original idempotency key; it must not blindly retry with a new version.

`purchase_request_status_history`, workflow histories, and approval decisions are immutable. Application logs and OTel traces are diagnostic evidence only and cannot reconstruct missing business history.

## Idempotency and Retry Records

**Command idempotency — Proposed**

The first slice requires an idempotency key for `create`, `submit`, `approve`, and `reject`.

- Scope is a fixed command scope such as `purchase.create`, `workflow.submit`, or `workflow.approve`.
- Key limit is 128 UTF-8 bytes.
- Uniqueness is `(tenant_id, scope, idempotency_key)`.
- The canonical request digest includes target ID, command, expected version, normalized safe fields, and actor context digest.
- Reusing a key with a different digest returns `idempotency_conflict`.
- Reusing a successful key returns the original resource IDs and versions without new business rows, history, or audit events.
- A transaction crash rolls back the idempotency row and business changes together.
- The same `operation_id` is retained for a replay; a genuinely new attempt has a causation link and a new execution/attempt ID.

The current routes do not show idempotency handling — **Transitional**. Cutover must either require the key or provide a formally documented compatibility adapter; silently generating a new key per HTTP request is not acceptable for critical writes.

**Retry records**

- `operation_idempotency.attempt_count` counts command handling attempts.
- `audit_outbox_attempts` records each relay delivery attempt.
- Future external execution uses a logical `workflow_execution` id plus separate attempt rows.
- A retry never creates a new purchase aggregate or changes the business idempotency key.
- Transient relay failures use bounded exponential backoff with jitter and a maximum attempt count.
- Authentication, schema, authorization, tenant, and permanent contract failures go to `dead_letter` and require operator resolution; they are not retried indefinitely.
- An expired outbox lease is reclaimable by one relay at a time.

**Retention — Proposed, policy pending**

- Idempotency rows: retain for at least 30 days after terminal completion, or longer than the documented client retry window.
- Outbox attempts: retain for 30 days after a verified `ledgered` receipt.
- Unledgered and dead-letter events are not automatically purged.
- The exact durations remain subject to the missing business and legal retention policy.

## Indexes, Query Shapes and Limits

Indexes are access-path driven and replace, rather than duplicate, the current unscoped indexes after cutover.

**Purchase detail**

```sql
UNIQUE INDEX purchase_requests_tenant_id_idx
  ON purchase_requests (tenant_id, id);

CREATE INDEX purchase_requests_requester_idx
  ON purchase_requests (tenant_id, requester, status, created_at DESC, id DESC)
  WHERE deleted_at IS NULL;
```

Query:

```sql
SELECT id, item_code, qty, requester, approver, approver_position,
       status, reason, created_at, submitted_at, resolved_at, version
FROM purchase_requests
WHERE tenant_id = ?
  AND requester = ?
  AND status = ?
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

**Workflow approval lookup**

```sql
CREATE INDEX workflow_candidates_lookup_idx
  ON workflow_work_item_candidates
     (tenant_id, candidate_type, candidate_id, work_item_id);

CREATE INDEX workflow_work_items_pending_idx
  ON workflow_work_items
     (tenant_id, status, decision_deadline, created_at, work_item_id);

CREATE INDEX workflow_decisions_instance_idx
  ON workflow_approval_decisions
     (tenant_id, workflow_instance_id, decided_at);

CREATE INDEX workflow_instance_history_idx
  ON workflow_instance_history
     (tenant_id, workflow_instance_id, version_after);
```

The pending-approval query resolves candidate IDs through the organization/authorization port and then queries candidate rows. Names and position labels are never used as keys.

**Other required indexes**

```sql
CREATE INDEX purchase_history_lookup_idx
  ON purchase_request_status_history
     (tenant_id, purchase_request_id, aggregate_version);

CREATE INDEX audit_outbox_ready_idx
  ON audit_outbox
     (delivery_state, next_attempt_at, created_at, outbox_id);

CREATE UNIQUE INDEX operation_idempotency_key_idx
  ON operation_idempotency (tenant_id, scope, idempotency_key);
```

Limits:

- First-slice list responses remain capped at 50 rows, matching current behavior.
- Pagination uses `(created_at, id)` keyset cursors; unbounded offset pagination is not introduced.
- `item_code`: 200 bytes maximum.
- Transitional `qty`: 64 bytes maximum.
- `reason`: 2,000 bytes maximum.
- Definition and authority snapshots: 64 KiB and 16 KiB respectively.
- Audit payload: 64 KiB maximum per event.
- No `SELECT *` in new read paths.
- No standalone low-selectivity `status` indexes unless an actual query plan demonstrates need.
- SQLite write transactions are short and contain no network calls. Busy timeout and maximum transaction duration must be configured and tested; current settings are **Missing**.

## Audit Outbox Transaction

**Atomicity — Proposed**

For every critical purchase or workflow command, the following commit is atomic:

```text
purchase state change
+ purchase/workflow history
+ approval decision or workflow state
+ operation_idempotency completion
+ local audit_outbox row
```

If the local outbox insert fails, the business transaction fails and rolls back. A successful HTTP response cannot mean that the business row committed without a durable local audit event.

The relay runs only after commit:

```text
claim pending row with lease
→ send the same event_id/event_key to audit-governance
→ record accepted/ledgered/indexed/archived receipt
→ release or retry lease
```

Remote calls are never made inside the SQLite transaction. Duplicate remote delivery is safe only if audit-governance treats the stable event ID as idempotent.

**Event mapping — Proposed, integration Missing**

Each event maps the execution context fields:

- `tenant_id`
- `operation_id`, `correlation_id`, `causation_id`, `trace_id`
- actor and initiator type/ID
- `on_behalf_of`, delegation, and capability grant references
- workflow and execution references where applicable
- aggregate type, ID, and version
- event type and schema version
- outcome and reason code
- redacted payload digest
- data classification and retention class

Default first-slice audit payload includes aggregate IDs, status transition, version, operation ID, and digests. It excludes tokens, passwords, session data, raw request bodies, authority credentials, and raw rejection text.

The three required audit-governance comparisons remain **Missing**:

1. Actual ingest path and transport.
2. Required fields and active `EventEnvelope` schema.
3. Receipt contract for `accepted → ledgered → indexed → archived`.

Until these are compared against the active governance implementation, the system must not claim `ledgered`, `indexed`, or `archived`. Local durable acceptance is not evidence of governance-ledger acceptance.

**Current notification behavior — Transitional**

The existing notification calls occur after purchase mutation and are not part of the business transaction. Notification failure must not reverse a committed purchase decision, but it also must not be mistaken for successful audit delivery. A separate integration outbox is a later slice if reliable notification delivery becomes a requirement.

## Expand Migrate Contract Plan

**Migration control — Proposed**

Add a versioned migration ledger:

```text
schema_migrations
  version       INTEGER PRIMARY KEY
  name          TEXT NOT NULL UNIQUE
  checksum      TEXT NOT NULL
  applied_at    INTEGER NOT NULL
```

The current inline `CREATE TABLE IF NOT EXISTS` and `ALTER TABLE` behavior is **Transitional** and must not remain the long-term migration authority.

**Expand**

1. Take a verified SQLite backup and record schema, row counts, status counts, and `PRAGMA integrity_check`.
2. Add nullable compatibility columns to `purchase_requests`: `tenant_id`, `created_by`, `updated_at`, `created_at` compatibility handling, `submitted_at`, `version`, `source_system`, and `trace_id`.
3. Create history, workflow, idempotency, outbox, attempt, receipt, and migration-ledger tables.
4. Seed the immutable `purchase-approval` definition version 1.
5. Create new tenant-scoped indexes without dropping old indexes.

No old column is removed or renamed in this phase.

**Migrate/backfill**

- Require an explicit configured deployment tenant. If it is absent, stop before modifying business data.
- Backfill `tenant_id` for every existing purchase row with that one configured value; do not guess.
- Backfill `created_by` from the existing requester subject and `updated_at` from `created_at`; mark the source as legacy migration.
- Set legacy aggregate `version` to `1`.
- Insert one `legacy_imported` history row per existing purchase. This records the observed snapshot; it does not fabricate the missing historical transition sequence.
- Existing `pending_approval` rows may receive a clearly marked `legacy_backfill` workflow instance and pending work item derived from the existing approver fields. Existing approved/rejected rows do not receive fabricated approval decisions.
- Backfill is resumable and idempotent through migration version, stable source marker, and existing unique keys.
- Invalid status, empty identifiers, tenant ambiguity, or duplicate relationships stop the migration rather than being coerced.

**Switch**

1. Route create/submit/approve/reject through application services and the typed aggregate command port.
2. Perform compatibility dual-write only inside the same transaction; the old column names remain readable.
3. Switch reads to explicit projections with tenant and deletion predicates.
4. Verify query plans and concurrency behavior.
5. Disable the old direct `setStatus` write path.
6. Move schema creation out of `PurchaseRequestStore` construction.

**Contract**

Only after all readers and writers have switched:

- Rebuild SQLite tables if necessary to enforce final `NOT NULL` and `CHECK` constraints.
- Remove obsolete unscoped indexes.
- Do not remove `qty`, `requester`, `approver`, or `approver_position` until their semantics and API compatibility are documented.
- Do not add a numeric quantity column until quantity evidence exists.
- Never combine dropping old columns with the first code release that reads new columns.

**Rollback boundaries**

- Before cutover: application rollback may leave additive columns and empty new tables in place.
- During backfill: stop and resume or roll forward; do not delete partially backfilled history.
- After dual-write begins: prefer binary rollback to a compatibility reader plus a forward data fix. Do not reverse-drop columns.
- After read cutover: a previous binary is rollback-safe only if it understands the expanded schema and ignores new tables; otherwise restore the compatible binary, not the old schema.
- A database restore is a disaster-recovery action, not ordinary deployment rollback. It must account for already delivered audit events and client retries.
- Audit ledger facts and external side effects cannot be undone by restoring SQLite. Use forward business correction or compensation.
- SQLite table rebuilds require a backup, maintenance window, integrity check, and tested restore path before execution.

## Deletion, Retention and Recovery

**Deletion — Proposed**

- The first slice has no delete API.
- `deleted_at` and `deleted_by` remain compatibility fields but are not a substitute for `cancelled`.
- All new reads use `deleted_at IS NULL`.
- If administrative deletion is later enabled, it is a purchase aggregate command that:
  1. verifies no active workflow,
  2. increments purchase version,
  3. records history and audit outbox,
  4. marks the row deleted,
  5. never cascades into history, decisions, or audit outbox.
- Physical deletion is not allowed for business rows in the first slice.

**Retention and redaction — Proposed, policy Missing**

- Purchase current state, workflow decisions, and state histories are retained; no automatic purge is enabled until the business retention policy is approved.
- Workflow definitions remain queryable while referenced and are retired rather than deleted.
- Audit-governance is the long-term audit authority. The local outbox is retained until a verified `ledgered` receipt, then for a bounded operational window.
- Legal hold overrides all local cleanup.
- Audit payloads contain status, IDs, versions, operation references, and digests; they do not contain secrets, tokens, raw request bodies, or authority credentials.
- Raw rejection text remains business data and is not copied into audit payloads by default.
- Authority snapshots contain policy and subject references, not access tokens or full grant material.
- Privacy erasure, anonymization, and legal retention durations require an approved policy that is currently **Missing**.

**Recovery**

- Restore SQLite to a new file, stop writers, run integrity and migration checks, and verify that all rows contain the configured deployment tenant.
- Reconcile `audit_outbox` by stable `event_id`/`event_key`; never resend with a new business event ID merely because the database was restored.
- Reconcile workflow references and report orphaned purchase/workflow rows before reopening writes.
- Audit-governance replay may rebuild audit evidence only. It must not directly mutate `purchase_requests`.
- Business recovery uses `recover`, `cancel`, or a domain-specific compensation command through the purchase aggregate port.
- Deployment rollback does not reverse approved/rejected state or any future external side effect. Irreversible work requires an explicit compensation contract.
- Current backup, restore, and disaster-recovery runbooks are **Missing** and are acceptance prerequisites.

## Rejected Designs

- **Separate workflow repository/service/database — Rejected.** The first slice keeps workflow facts inside `sverpweb-stable`; no new repository is created.
- **Workflow SQL against `purchase_requests` — Rejected.** Only the purchase aggregate module may write purchase tables. Workflow calls the typed command port.
- **Shared-instance multi-tenancy — Rejected.** The deployment remains single-tenant. A required `tenant_id` detects context mistakes but does not enable multiple tenants in one instance.
- **Client-selected tenant or department — Rejected.** Tenant and department are server-derived and authorization-checked.
- **Direct HTTP audit call as the only audit guarantee — Rejected.** The current post-commit behavior is Transitional; critical changes require an atomic local outbox.
- **Audit ledger as business-state authority — Rejected.** Audit governance records evidence and cannot restore or mutate purchase state.
- **One generic status field for purchase, workflow, work item, and execution — Rejected.** Each lifecycle has its own enum, version, and history.
- **ORM entity used as DTO or domain model — Rejected.** Mapping boundaries are required.
- **Free-form JSON update or Agent-provided approval text as authorization — Rejected.** Commands, policies, and transitions are typed and server-validated.
- **先查后插 idempotency — Rejected.** The database unique key is the final concurrency defense.
- **Invented business number or quantity conversion — Rejected.** No request-number evidence exists, and quantity semantics are unknown.
- **Physical deletion of history or audit events — Rejected.** Corrections, cancellation, and compensation are append-only facts.
- **Creating generic execution and compensation machinery in this approval slice — Rejected.** Those tables and side effects are deferred until a concrete irreversible purchase command is specified.
