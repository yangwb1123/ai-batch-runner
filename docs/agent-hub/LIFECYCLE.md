# Hub 服务停止、单写者所有权与重启

本页说明`abr fleet serve`的本地生命周期边界；不是持久服务已安装、生产恢复已验收或部署批准。
适用于默认只读与显式Web控制配置，不更改任何client、grant、scope或Gateway授权。

## 有序停止

POSIX主线程运行的Hub CLI处理SIGTERM/SIGINT：信号处理器只记录停止请求，不做网络/数据库
I/O、不抛出异步异常、不获取线程锁，也不在服务线程里调用会死锁的`BaseServer.shutdown()`。
主循环最长每250ms检查停止标记；已经收到停止标记的服务器不再接收新的HTTP工作。
只在监听器成功创建后启动Compute/Integration后台worker，避免端口绑定失败仍启动外部投递。

退出时：
1. 关闭请求准入及监听器，仅中断**本服务器接纳的**活动HTTP socket，让慢请求的读写返回。
2. 等待已接纳handler完成，保持原并发上限32。HTTP drain默认15秒，共享同一monotonic截止
   时间，持续请求或重复信号不延长；Python内嵌调用`server_close(drain_timeout=...)`只接受
   `(0,30]`内的有限数值，不新增远程或CLI调节入口。
3. 关闭Web内存会话并清理后台worker；任一清理失败仍尝试清理后续组件和数据库。
4. 关闭数据库准入，确认没有仍被接纳的SQLite连接；未完成时不能报告正常退出。

HTTP drain超时明确失败，CLI返回非零；不会假称已经停止全部执行者或删除现场。
15秒是**HTTP请求收尾预算**，不是整个进程/所有可选外部适配器的硬截止时间。
Compute/Integration保留各自的原有关闭与传输约束；需要持久运行时，应由明确拥有该进程的
supervisor配置最终停止时限。强制终止是另一种结果，不能记成有序停止或自动重放。
本轮没有安装systemd服务、修改现有supervisor或控制任何现场进程。

## 存储启动准入与初始化

正常启动在配置检查之后、监听器和后台worker之前执行以下准入；`--check-config`仍然
不打开数据库，因此配置预检通过不代表存储可启动。

- 存储保护要求POSIX的no-follow、非阻塞文件打开、uid和fd chmod能力；缺少时拒绝启动，
  不静默降级。路径最多4096字节/64个组件；先限制输入再解析父目录别名，数据库本身不
  跟随符号链接。祖先须由当前uid或root拥有，不可group/world写（可信sticky目录除外）；
  直接父目录必须是当前uid拥有且不可group/world写的目录，不自动chmod接管目录。
- 先接纳并获取原有永久`.lock`，再创建/打开数据库。锁须为空的、当前uid拥有的单链接
  普通文件；竞争者不能创建数据库或更改已占用文件的权限。任何启动异常都清理本次fd，
  不删除锁文件、强破锁或清理其它进程。
- 主库与`-wal/-shm/-journal`拒绝链接、特殊文件和其它uid；附属文件还必须已是私有权限。
  无主库/空主库的孤立附属文件拒绝，不删除它们后启动一份空库。已有不安全路径需要
  操作员先核对原所有者与状态，不能自动接管。
- 持锁后先通过SQLite `mode=ro`读取真实视图中的`user_version`，包含已提交的WAL内容，
  而非只读主文件头。仅保留原有版本0/1兼容；未知版本或非SQLite文件在chmod、WAL模式
  变更与DDL之前失败。SQLite只读打开仍可能更新共享内存协调信息，不宣称整个文件族
  字节完全不变；版本拒绝不改写主库/WAL数据。不要改小版本号来绕过拒绝。
- 兼容、已拥有的普通主库仍可从旧权限收紧为0600。核心表、会话创建/关闭、操作索引和
  compute授权表在同一个`BEGIN IMMEDIATE`事务内初始化，`user_version=1`同事务提交。
  DDL失败回滚这些表/版本的部分修改；不是所有可选组件的全局迁移事务，也不意味着
  已进行的安全权限/WAL模式变化或新建空文件被回滚。失败现场保留，不自动删除/重试。
- 每次SQLite连接前后重新核对目录、主库及锁的inode和附属文件。运行连接使用`mode=rw`，
  路径消失不能自动重建空库；路径/权限变化拒绝新连接，不修改替换物。已接纳事务仍可能
  完成，这不是对敌对同uid/root或不遵守锁的写者的隔离保证，也不是备份/恢复功能。

schema版本、租户、generation、幂等键与业务数据契约不变。仍需按实际存储环境验证升级、
恢复和回退，不能把可识别的版本号当作完整数据正确性或生产验收。

## SQLite所有权

`HubStore.close()`立即拒绝新连接，但**最后一个已接纳连接真正关闭前保留原有`.lock`锁**。
因此，关闭请求与正在提交的事务竞争时，第二个Hub仍会以`store_in_use`被拒绝。数据库
连接关闭失败（例如从错误线程关闭）不释放所有权，不能靠重复请求绕过。

需要确认闭合的内嵌调用可使用：

```python
store.close()
store.require_drained()  # 未关闭或仍有连接时抛出HubStoreError，不破锁、不等待无限重试
```

私有`store._connect()`返回连接的context manager现在在提交/回滚后**也关闭连接**；不能
在`with`块之外继续复用它。显式`close()`仍幂等；SQL、WAL、同步级别、schema版本、租户、
幂等键及generation契约不变。这里是协作进程的生命周期保障，不是对敌对同uid文件替换、
数据库路径别名、活动文件拷贝或跨平台锁实现的额外安全证明。

## 重启不等于重放或回滚

中断HTTP连接会让客户端看不到最终响应；已经受理的数据库事务仍可能提交。
停止请求、客户端超时和退出网页均不代表Agent代码改动、外部写入或已提交事务已回滚。
恢复后先按原请求ID/幂等键只读核对，不能因没有收到响应就生成新key再执行。

- Hub实例/请求/事件账本继续来自同一SQLite状态；不删除数据库/WAL来“修复启动”。
- Web登录会话仍在内存中，重启后重新登录；这里不引入持久Cookie或跨重启token缓存。
- 观察型Gateway仍只登记/心跳；执行型Gateway、provider的停止/重启及未知副作用恢复须
  独立验收。Hub退出不会自动终止远端Agent，也不授权接管其generation。
- 不提供将活动SQLite/WAL直接拷贝成备份的捷径；一致性备份、恢复演练、版本回退和实际
  存储故障验证仍是发布准入项，见[WEB_RELEASE.md](WEB_RELEASE.md)。

## 已实现的隔离验证与未覆盖项

`tests/test_hub_lifecycle.py`使用真实本地HTTP/SQLite，覆盖慢请求中断、已受理事务继续提交、
关闭期间第二写者拒绝、drain超时、错误线程关闭及连接构造失败。`tests/test_hub_server_signals.py`
覆盖32请求上限、信号handler恢复、worker启动失败和清理异常，并在POSIX上启动真实CLI子进程，
分别发送SIGTERM/SIGINT，确认退出0、重启后同一请求仍为queued且不会自动创建/执行会话。
测试仅终止自己的Popen；没有调用真实SSO、provider或生产项目。Windows进程终止语义不由
这组POSIX用例证明；非POSIX不运行这两条真实信号用例。

`tests/test_hub_store_admission.py`与`tests/test_hub_store_paths.py`覆盖版本拒绝不改库、
五段核心DDL同事务回滚、兼容升级、锁竞争/异常fd清理、危险文件族、路径替换与连接不重建。
自有SQLite子进程用`os._exit`保留已提交WAL，验证从真实视图读取版本；不是断电或生产恢复
演练。uid拒绝还包含受控stat替身，不冒充真实跨账号或跨平台隔离验收。

这些测试不替代真实身份、公开HTTPS入口、生产Gateway、外部审计、当前镜像安全扫描、
异常断电/SIGKILL、长时间运行、完整supervisor期限或现场存储恢复验收。
