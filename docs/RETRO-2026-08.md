## 2. 发现与行动项

### F1. gate 无 VERDICT 行是高频模式（22 次，占 gate 失败 1/3）
模型不按"最后一行 VERDICT: PASS - reason"输出是真实高频行为。
- 已落地：VERDICT 正则容忍 markdown 加粗（runner + pipeline 双修）
- **待办**：gate 任务模板强化格式指令（"最后一行必须以 VERDICT: 开头，禁止加粗/引用/代码块"），在 repository-campaign-pipeline.yaml 与 quickstart 模板中统一

### F2. 19.7% 任务失败率——失败签名与反馈是核心防御
185 次失败中协作者日志 167 次为 "agent exited 1"（一般性失败，无具体签名）。
- 已落地：失败签名拒绝（quota/network/认证）已有；validator feedback 重试闭环已有
- **待办**：`agent exited 1` 细分——在 runner 日志中附 stderr 尾部摘要（当前只记 exit code），便于 retro 定位失败根因

### F3. 25 次锁冲突 → 排队是刚需
协作者 4 仓库并行撞锁 25 次（每次手工重跑）。
- 已落地：`--wait-lock MINUTES`（排队）+ `pi-batch ps`（可见性）

### F4. 18 次超时——热点已定位：META 对抗审查角色任务
- **已落地**：retro 增加"超时上下文"证据（timeout 行前后 3 行）
- 分析显示 5 次超时全部在 adversarial_review 的 meta 角色任务
  （security_engineer/architect/protocol_expert 长文档生成 >900s）
- **待办**：meta 角色任务支持独立超时配置（长审查文档需要更大预算），
  或默认对 meta 任务放宽到 1200s

### F5. 熔断 151 次——毒任务防护在真实长跑中不可或缺
- 设计验证：circuit 隔离 + env-signature 停环正确工作
- 无新增行动项

### F6. 分析器自身的校准
- stage_failed 正则最初把"1/1 succeeded"误计为失败（33 vs 真实 7）——retro 工具本身也经过一轮真实数据校准（计数语义修正 + 测试固化）
