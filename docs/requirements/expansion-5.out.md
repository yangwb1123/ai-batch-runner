第五轮与已收敛路线图的重叠约 95%。本轮 delta 是 4 个微项 + 2 个新机制（judge 验证、审批点），其中有一个点（并发角色 × 全仓验证器）是四轮以来最有价值的代码级发现。逐条核验如下。

## 本轮新内容的核验

**N1：in-flight 任务崩溃后双重计费 — 属实，且比你描述的更糟。** `_spawn_agent` 用 `start_new_session=True` 把 agent 放入独立进程组，runner 被 SIGKILL 时进程组**不会**被杀——agent 子进程成为孤儿继续跑完整个调用（账单已出），输出因管道断裂丢失；重启后 `--reuse` 看不到输出文件 → 重跑 → 双重计费。状态机的 `running` 态记录正是检测手段（重启时发现 running 残留 → 告警而非静默重跑）。

**N2：并发角色 × 全仓验证器竞态 — 属实，本轮最有价值的发现。** meta 角色任务的 agent 带默认工具（无 `--tools` 限制）、cwd 是仓库根——角色 A 的 agent 正在写文件时，角色 B 的输出正在跑全仓扫描类验证器（本仓库的 `pyquality: python {cwd}/quality.py {cwd}`、`go build ./...` 都是），读到半成品 → **误报失败 → 触发重试 → 烧钱**。单批 parallel 模式同样存在（agent A 编辑 vs agent B 的验证）。两点修正：① "git 交错提交"断言偏弱——`_git_commit_stage` 在阶段结束后串行执行，meta 内部不交错；真实风险只在双实例并发（上轮已确认无锁）。② **现有架构已有正确的修复槽位**：全仓类验证器本就该放阶段级 `commands`（阶段完成后串行执行），而非 per-task `validate`——最便宜的第一步是文档约定，可选代码修复是给验证器加 `scope: repo` 标记延迟到阶段末。

**N3：judge 验证 — 好消息：90% 今天就能用。** 验证器注册表就是"shell 命令 + exit code + `{output}` 替换"，一个 judge 校验器就是 `pi -p "<rubric> {output}"` 后按分数退出的命令——零代码可挂。缺的只是内置 rubric 约定和便利封装（解析分数而非裸退出码）。"假通过 gate"属实：`_GATE_VERDICT_RE` 只查 `VERDICT: PASS` 行存在，不查理由、不查与内容矛盾——但 gate 阶段本身已支持 `validate_cmd`，judge 校验器可以直接挂在 gate 阶段上堵住这个洞。

**N4：人工审批点 — 新机制，属实缺失。** 实现形态清晰：`run_pipeline` 阶段间检查 `approval: true` → 等标记文件/确认命令，带超时自动拒绝（fail closed），与 gate 的裁决语义一致。与 N3 一样属于"制度声明 → 强制门禁"的工程化，改动小。

**N5：per-agent 配置分层 — 上轮已提，新增细节成立。** `_AGENT_ERROR_PATTERNS`（`runner.py:31`）是硬编码全局元组，换 agent 二进制后签名表确实不适用；会话标志同理。与异构路由（G 线）合并实现。
