我已按要求只读取了 README.md、AGENTS.md 和 `pbatch/` 五个文件的前 40 行（未扫描 docs/、tests/、prompts/、examples/）。以下从架构师/产品经理视角给出 5 个高价值扩展方向，均基于现有机制的真实缺口。

---

## 方向 1：成本与上下文预算治理（Budget Governance + Context Watermark）

**现状**：`--max-rounds 0` 意味着无限轮循环，但唯一的停止条件是"全部通过"；`--retries` 只控制次数，没有任何 token/费用维度。共享会话（`--session-mode shared`）跨轮、跨阶段无限延续上下文，会话 id 由 `--session-name` 派生可复现——意味着长期运行中上下文必然逼近模型窗口上限。

**扩展点**：
- 任务/阶段/批次级 token 与费用记账（解析 CLI 输出或 provider 计费接口）
- 会话续接前的上下文水位估算：接近上限时自动**轮转会话**（session rotation，保留旧会话 id 用于追溯）
- 成本上限熔断（类比 max-rounds：`--max-cost N` 达到即停，与"无限循环"正交）

**为什么需要**：7×24 无人值守的核心承诺是"可控地花钱换产出"。当前最危险的边界情况恰恰是：一个永远过不了 gate 的任务 + `--max-rounds 0` = 无限烧钱；共享会话触顶后 agent 输出退化（截断/遗忘早期约束），且这种退化**exit 0、有内容、不匹配任何失败签名**——现有的失败检测体系对它完全失明。没有预算护栏，无人值守的"无人"二字就变成了风险而非优势。

---

## 方向 2：失败分类策略矩阵 + 任务级熔断 + Validator 反馈再生

**现状**：失败签名是扁平列表，统一走"拒绝 → 退避重试"，但不同失败的最优对策完全不同：quota 类应等待窗口；auth 类重试毫无意义应立刻停并告警；**validator 失败**（gate 拒绝产物）当前只能盲目重试同一 prompt——而验证器输出恰恰是最有价值的修复信号，却被丢弃。

**扩展点**：
- 失败分类 → 策略表（per-class action：wait / retry / **stop+notify** / regenerate）
- 单任务失败预算：连续 K 次失败即隔离出队列（quarantine）并上报，不再占据无限轮循环的资源
- **Regeneration 模式**：validator 失败时把验证器输出（如 `python cli.py check` 的报错）回喂给 agent 作为下一轮 prompt 上下文，形成自修复闭环

**为什么需要**：这是收敛性与成本的双重边界。当前"无限重试同样内容"假设失败是瞬时的，但实际上很多失败是确定性的（prompt 歧义、gate 标准不可达）——无限重试等于把预算烧给一个注定失败的任务。而 validator 反馈再生能把"验证失败"从终点变成迭代信号，这正是工程门禁（`make ci` 等价物）与 AI 产出之间缺失的桥梁。

---

## 方向 3：输入指纹与产物缓存（`--reuse` 2.0）

**现状**：`--reuse` 的判定是"输出文件存在即跳过"。这意味着上游 `from_dir` 内容变化、prompt 修改、模型切换后，陈腐产物仍会被当作有效输入喂给下游——断点续跑的正确性完全建立在"存在即有效"的脆弱假设上。

**扩展点**：
- 对 `(prompt + 输入文件内容 hash + agent bin + model + validator 集)` 计算指纹，写入 sidecar（或产物头部元数据），**指纹命中才复用**
- 指纹未变时跳过 git commit / 归档，消除无意义提交噪音
- 顺带解决 `aggregate: true` 的性能问题：证据折叠现在每次全量重读拼接，可改为基于上游指纹的增量合并

**为什么需要**：`--reuse`/断点续跑是 7×24 运营的基石，但"存在即有效"会让**陈腐数据静默污染下游决策**——gate 可能基于过时的设计文档放行。这是正确性缺陷而非优化项。指纹缓存同时带来性能收益：CI 场景下可跨目录复用缓存，未变更的任务从"跳过"升级为"零成本跳过"。

---

## 方向 4：调度性能——429 感知的自适应并发 + 阶段间流水线化

**现状**：并行度是固定 `ThreadPoolExecutor`（`--workers` 静态配置）。任务集体触发限流时，所有任务一起进入 30s 退避——既慢又浪费；流水线阶段严格串行，下游阶段连 prompt 预渲染都不做；AND 语义的多个验证器串行执行。

**扩展点**：
- **自适应并发**：观测 429/速率类失败频率，动态下调有效 worker 数（限流恢复后再回升），而不是固定线程池+集体退避
- **阶段间流水线化**：下游阶段的 prompt 渲染、输入装配（aggregate 合并）提前到上游执行期间完成
- 验证器按 AND 语义**并行执行**（当前串行等待全部完成）

**为什么需要**：性能在这个项目里不是"快一点"的问题，而是**吞吐与稳定性**的问题——固定并发在限流场景下放大失败面（集体退避 = 任务全部延期），7×24 场景下一天的无效等待就是实打实的成本。这些优化都不改变语义，纯属执行层收益，风险低、见效快。

---

## 方向 5：结构化遥测、运行状态 Journal 与通知钩子

**现状**：`--log-file` 是给人看的追加文本；runner 进程自身崩溃（OOM、机器重启）后，轮循环只能靠磁盘上的输出文件推断进度——已重试次数、退避进度、会话 id、gate 中间结果全部丢失；7×24 运行中 gate FAIL 或任务全部失败时，没有任何机制把"人"叫醒。

**扩展点**：
- JSONL 结构化事件流：`task_started / retried / failed / gate_rejected` 等事件，带 duration、exit code、retry count、指纹——可直接对接监控系统
- **状态 journal**：轮循环的中间状态落盘，崩溃后从 journal 原地续跑（而非仅靠"跳过已有输出"）
- 通知钩子：失败预算耗尽、gate REJECTED、成本熔断触发时推送到 webhook/Slack/邮件

**为什么需要**：7×24 无人值守缺最后一环——**事故唤醒机制与崩溃恢复**。当前"输出文件存在"是唯一的持久状态，等于把恢复能力建立在对 crash 时机的好运上；而无人值守场景中 gate 被拒正是最需要人工介入的时刻，却只能等人主动来看日志。这决定项目能否从"脚本工具"升级为"可运维服务"。

---

**补充（值得留意但未单列）**：信任边界在输入侧还有一个洞——`from_dir`/`@file.md` 会把**不可信仓库内容**直接内联进 prompt，可携带注入指令；且产物大小无上限（agent 可写 GB 级文件撑爆磁盘）、提交前无敏感信息扫描。若工具要用于 CI 或扫描第三方仓库，这是必须补的一层。

---

**优先级建议**（若资源有限）：方向 2（熔断+反馈再生）与方向 1（成本护栏）直接决定 7×24 长期运行的安全性，应最先做；方向 3 是正确性债务，建议紧随其后；方向 4、5 是规模化运营的收益项。
