---

## 1. 失败治理升级：失败分类 + 熔断隔离 + 验证结果回喂（自愈闭环）

**现状缺口**：失败检测是静态正则签名（额度/网络/认证），拒绝后统一走指数退避重试。`--max-rounds 0` 意味着"永远重试直到通过"——但系统不区分**瞬时失败**（429、断网）和**永久失败**（认证失效、prompt 不可行、验证器本身坏了）。验证门禁失败时只是删临时文件重跑，agent 不知道"为什么失败"，每次重生成都是全新盲试。

**扩展内容**：
- 失败分类三态：transient（可重试）/ permanent（不重试，标记 poisoned task）/ environment（验证器配置错误，应熔断整个阶段而非任务）；
- 永久失败任务进入隔离区并告警，不再进入下一轮（防止 7×24 空转烧钱）；
- 验证器失败时把 stderr/exit code 摘录回喂给 agent 重新生成（"你的输出没通过 `gofmt -l`，这是报错……"），而不是从头再来——这是 token 效率提升最大的单项改进。

**为什么需要**：当前模型的隐性成本是"确定性失败无限重试"。在真实 7×24 场景中，认证过期或验证器缺依赖（如 gofmt 未安装）会让整个轮循环以最高频率空转数小时，账单和日志全是噪音；而验证失败不回喂，等于让 agent 在盲区里迭代，一次能收敛的问题要花 3-5 倍 token。

## 2. 成本与上下文治理：计量、预算上限、模型分级路由

**现状缺口**：全工具链没有任何 token/费用计量。7×24 无人值守 + `--max-rounds 0` + 滚动分析（`for i in ...`），是"成本无上限"的架构。共享会话模式下，长流水线的会话上下文持续增长，接近窗口上限时模型质量会静默劣化——这是目前完全不可见的边界情况。

**扩展内容**：
- 每次任务记录输入/输出 token 估算（按 prompt 字符量 × 模型单价），汇总到决策日志或独立账单文件；
- 全局预算上限：`--budget-max` / 日预算，触顶即停止轮循环并告警；
- 模型分级：探索类任务（meta 编排、初稿）用便宜模型，裁决门、实现类任务用强模型——按阶段声明 `model_tier`，而不是全局一个模型；
- 共享会话上下文水位监控：超阈值时提示或自动切换新会话。

**为什么需要**：无人值守工具的第一风险不是功能缺失而是**失控成本**。没有计量就没有预算，没有预算就不能安全地把 `--max-rounds 0` 交给 CI 或 cron。模型分级则是把"同一 agent 二进制、统一 flag"的抽象进一步推向"按任务价值调度算力"，是 ROI 最高的配置扩展。

---

## 3. 运行状态持久化与可观测性：结构化状态存储 + 停滞检测 + 告警钩子

**现状缺口**：当前状态推断靠文件存在性（`--reuse` 看输出文件在不在），运行记录只有追加式 `--log-file` 文本和决策日志。崩溃后无法回答"这批跑到哪了、哪些任务重试了几次、失败都是什么类别"；没有停滞检测——如果所有任务连续 N 轮以同一类别失败，系统会安静地一直转圈。

**扩展内容**：
- 每任务一条结构化状态记录（JSONL：状态、轮次、重试数、失败类别、耗时、输出路径、校验结果），原子写入，作为 `--reuse`/resume 的权威依据（文件存在性降级为启发式）；
- 停滞检测：连续 K 轮无新增成功且失败类别分布不变 → 判定"收敛失败"，停止并报告，而不是无限循环；
- 告警钩子：任务失败/预算触顶/停滞时调用 webhook 或 exit-code 约定，便于接入监控系统。

**为什么需要**：7×24 的前提是可监督。现在"无人值守"实际上是"无人能查"——文件系统不是状态数据库，文本日志不可查询。结构化状态是后续一切运营能力（统计、告警、恢复、审计）的地基，也是解决"崩溃后从哪继续"这个最痛的边界情况的正确方式。

## 4. 调度与资源治理：provider 级并发限速、资源感知并行、产出新鲜度校验

**现状缺口**：并行模式用 `ThreadPoolExecutor` 直接起 N 个 agent 进程，N 个并发请求同时打向同一个 provider API——速率限制是全局的，worker 越多越容易触发 429 风暴，然后全体退避 30s，吞吐反而崩掉。此外 `--reuse` 只看文件存在：**已存在的旧产物不会重新过验证门禁**——改了验证器或代码后，陈旧产物会被静默当作成功。

**扩展内容**：
- provider 级并发上限（每 agent 二进制/每模型令牌桶），并行 worker 共享限速，限速触发时协调退避而非各自为战；
- 本地资源感知：按机器 CPU/内存决定有效并发数（agent 进程是重量级的）；
- 产出新鲜度校验：`--reuse` 时对已有产物做（可选）年龄/内容哈希检查，或至少支持"reuse 也跑验证器"的模式，避免陈旧产物过关；
- 并发安全：同一输出路径的写锁/原子 rename 已有基础，但需防两个 7×24 实例跑同一工作目录的竞态。

**为什么需要**：这是性能与正确性的交汇点。并行度的正确值不是用户拍脑袋定的 worker 数，而是"provider 限速 × 本地资源"的约束解；而 `--reuse` 的语义漏洞（陈旧产物当成功）会让整个验证门禁体系在续跑场景下被悄悄绕过——验证器链条只在首次写入时生效过一次。

---

## 5. 输入驱动的增量执行：内容寻址与变更检测（不做无用功）

**现状缺口**：任务重跑的依据是"输出不存在或失败"，而不是"输入是否变化"。滚动分析场景中，输入（代码库）没变时每轮仍会全量重跑；`from_dir` 目录里 100 个文档改 1 个，会重跑全部 100 个任务。

**扩展内容**：
- 对任务输入（prompt、`from_dir` 文件集、上游产出）计算内容哈希并记录，输入未变 + 输出存在 → 跳过（`--reuse` 从"文件存在"升级为"输入指纹未变"）；
- 可选 diff 注入：`from_dir` 只把变更文件作为上下文传给 agent，并把"相对上次的变化摘要"作为提示词前缀，让增量分析真正增量；
- 配合方向 3 的状态存储，实现"输入指纹 → 任务结果"的可复现缓存层。

**为什么需要**：当前 7×24 轮循环对不变输入的重复计算是纯浪费——同样花 token、同样过门禁，产出却不会变。内容寻址让 `--reuse` 从"脆弱的启发式"变成"有语义的缓存"，长期滚动运行（200 轮那种）的成本可以降一个数量级，同时保留"输入变了必重跑"的正确性保证。

---

**一句话总结**：前两个方向（失败治理、成本治理）解决的是"7×24 无人值守会不会失控"的**信任问题**，是产品能规模化使用的门槛；后三个（可观测性、调度治理、增量执行）解决的是"跑得省、跑得快、跑得可查"的**效率与运营问题**。其中方向 1 的"验证失败回喂"和方向 4 的"reuse 新鲜度校验"是投入产出比最高的两个点，建议优先。
