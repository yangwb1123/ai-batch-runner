## 方向 1：成本与额度治理边界（Budget & Quota Governance）

**现状与边界情况**：系统已有 rate-limit 失败签名和退避重试，但那是**事后被动**的——先撞墙再等 30s。而 7×24 轮循环（`--max-rounds 0`）+ meta 阶段并发角色 + `--retries` 组合起来是一个"成本上不封顶"的执行模型：最坏情况不是任务失败，而是**任务一直"成功"地烧钱**（例如 agent 陷入重复自我完善、meta 编排者反复挑选新角色）。

**扩展内容**：
- 声明式预算上限：按任务/阶段/轮次/天设置 token 或美元阈值，超限熔断（停止、降级为小模型、或仅告警）。
- 成本归因与核算：run manifest 记录每次调用的模型、token 消耗、耗时，按 pipeline/stage/role 维度汇总，让"一次无人值守跑了一晚上"事后可解释。
- 预算预警与速率自协调：worker 数不应只受 `--workers` 控制，还应与已知的厂商速率配额联动，**主动限速**而不是被动撞 429。

**为什么需要**：无人值守系统从"工具"升级为"可运营平台"的分水岭就是资源边界。没有预算上限，7×24 的部署承诺在财务上是不可接受的；这是产品化第一优先级。

## 方向 2：结构化 Run Manifest 与检查点恢复（Observability + Checkpointing）

**现状与边界情况**：`--reuse` 的跳过判据是"输出文件是否存在"。这有两个边界漏洞：① 文件存在但**陈旧**——输入（from_dir 文档、上游产出）已演进，旧产物被静默复用；② 文件存在但内容损坏/为空（非本工具写入的占位文件）。`--log-file` 是平铺时间戳文本，无法程序化查询"哪个任务、哪一轮、什么结果"。

**扩展内容**：
- 每轮写入结构化 manifest（prompt hash、输入文件 hash、agent 版本、耗时、成本、验证结果、退出码），`--reuse` 从"存在性跳过"升级为**基于内容 hash 的增量缓存**——输入没变才复用，变了自动重跑。
- 崩溃恢复：runner 被 SIGKILL（服务器重启）后，从 manifest 恢复轮次进度，而不是整批重跑——这直接关系到 7×24 的可靠性承诺。
- 性能收益：hash 缓存让滚动分析类任务在输入稳定时几乎零成本，这是最大的性能优化点（比微调 `_read_stream` 的 I/O 高几个数量级）。

**为什么需要**："存在即成功"在输入静态时成立，但流水线的本质就是输入不断演进；静默复用过期产物会污染证据链，比失败更危险（失败可见，过期不可见）。

---

## 方向 3：验证门禁从"布尔命令"升级为"结构化多级门禁 + 验收闭环"

**现状与边界情况**：验证器是 shell 命令的 AND 布尔；gate 特例是"输出里出现 `VERDICT: PASS` 行"。对代码生成类任务，`build`/`gofmt` 通过只能证明"语法可编译"，证明不了"行为正确"——AI 产出最大的风险恰恰是**编译通过但语义错误**，现有门禁体系对此是盲区。

**扩展内容**：
- 结构化验证器协议：验证命令输出 JSON 报告（pass/warn/fail + 类别），warn 不阻断但写入决策日志，error 阻断——分级放行而非一票否决。
- 验收闭环任务类型：门禁从"检查产物"升级为"**自动生成测试 → 执行测试 → 结果作为 gate 证据**"，把验证从静态检查变成行为验证。
- 结构契约校验一等公民：要求产物符合 JSON schema / 固定 markdown 结构（目前只有 VERDICT 行这一个结构特例），失败签名检测的姊妹机制。

**为什么需要**：AI 产出的信任只能靠证据链建立。布尔门禁只防"崩溃级"失败，防不了"正确性级"失败；结构化 + 验收闭环是让流水线能真正自动放行代码类交付物的前提。

---

## 方向 4：异构 agent 路由与跨厂商交叉验证（Heterogeneous Routing）

**现状与边界情况**：`agent.bin` 是全局单一配置，会话标志也是全局的。但对抗审查（meta 阶段 security_engineer 挑战架构、qa_lead 找缺陷）本质是"同一大脑的分身互搏"——同一模型有**系统性的幻觉模式和盲区**，交叉验证的独立性被稀释。Task 模型已有 `model` 字段，但缺 agent/provider 维度，异构能力是半成品。

**扩展内容**：
- per-task/per-stage 声明 agent + model + provider，任务级能力路由：简单分析用小模型（省成本、快），复杂推理用强模型，验证类任务用确定性工具。
- 对抗性 meta 角色**默认跨厂商执行**：架构师用 A 厂商、安全审查用 B 厂商，让"独立视角"名副其实。
- per-agent 适配层：不同 CLI 的会话标志、超时语义、退出码约定不同，需要把 `session_flags` 从全局降为 per-agent 配置。

**为什么需要**：交叉对抗是本工具最核心的差异化能力，其价值完全取决于视角的独立性；同时异构路由是成本优化的最大杠杆（目前是"一把牛刀切所有菜"）。

---

## 方向 5：产物信任链与内容安全（Provenance & Content Safety）

**现状与边界情况**：安全边界已覆盖路径穿越、失败签名、角色名 sanitize——但**内容层**是空白：`from_outputs` 和 meta 证据折叠把 agent 输出直接喂给下一个 agent，构成 prompt injection 的传播面（上游被污染 → 下游全链污染）；`git_commit: true` 自动提交意味着**任何敏感信息泄露都会自动进入版本历史**，且不可轻易撤回。

**扩展内容**：
- 产物溯源元数据：每个产物记录 provenance（产出任务、agent、prompt 版本、时间、上游产物 hash），让证据链可追溯、可审计。
- 提交前内容安全 gate：密钥/凭据/内网路径等敏感模式扫描，命中即拒绝落盘/提交（复用现有 validator 机制即可挂载）。
- 注入防护：对进入下一阶段的输出做结构隔离（把上游内容作为"数据引用"而非"指令"传给下游 agent 的 prompt 构造层）。

**为什么需要**：证据折叠是流水线的引擎，链越长被注入污染的风险越大；而"自动 git 提交"是泄露的最高风险出口——这两者叠加，是当前安全模型里最值得补的一环。

---

**优先级建议**：方向 2（正确性/可靠性根基）与方向 1（财务安全）并列第一梯队；方向 3 次之；方向 4、5 是差异化与信任升级。其中方向 2 的 hash 缓存同时解决可靠性、陈旧产物 edge case 和性能三件事，投入产出比最高。
