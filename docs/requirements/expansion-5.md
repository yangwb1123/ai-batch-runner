## 1. 成本预算治理（Cost Governance）与熔断

**现状**：`--max-rounds 0`（无限轮循环）+ 并行 workers + 共享会话 = 无人值守下 token/API 消耗几乎无上限。已有失败签名里的 quota/rate-limit 是被动防御——等供应商来掐你，而不是你主动控制。

**为什么需要（边界场景）**：
- 某轮循环中 prompt 或代码库变化导致 agent 反复重试同一失败任务，预算在重试指数退避的间隙被烧掉；
- 并行 4 workers × 长 pipeline（十阶段评审），单次运行的 API 账单可能超出预期一个数量级；
- 当前"任务失败=不落盘"只保证产出质量，不保证**花钱上限**。

**建议形态**：运行级/任务级预算上限（按模型单价 × 预估 token，或按次数配额），超预算触发熔断（暂停新任务、保留现场、决策日志记录原因）；每次运行输出结构化成本报告（每任务耗时、重试次数、估算成本），供 `--log-file` 与决策日志联动。这是 7×24 产品化的**第一信任门槛**。

## 2. 崩溃安全的任务状态机与输入指纹（幂等续跑升级）

**现状**：`--reuse` 靠"输出文件是否存在"判断跳过——这是启发式而非状态。进程被 SIGKILL/断电时，运行中的任务（已花钱、输出未落盘）进度丢失；且代码库变化后旧输出仍被当作有效复用。

**为什么需要（边界场景）**：
- 24×7 无人值守中宿主机重启：in-flight 任务既没产出也没失败记录，重跑即双重计费；
- 滚动分析场景（同一 session 反复跑）：代码库已演进，但 `--reuse` 仍复用昨天的过时产物——**静默的陈旧结论**比失败更危险；
- 共享会话续跑依赖 `--session-name` 派生，缺磁盘状态时无法知道"上一轮到底跑到哪"。

**建议形态**：任务级状态文件（pending/running/done/failed + 时间戳），启动时恢复中断状态；`--reuse` 从"文件存在"升级为"输入指纹比对"（prompt + 上游产物 + 关键文件 hash），有变化才重跑。这是把 24×7 从"尽力而为"变成"可审计"的关键。

---

## 3. 供应商感知的速率控制与并发资源隔离

**现状**：并行模式只有 `--workers` 和成功任务间的 `--min-interval`，对同一模型/供应商的并发请求无节流；meta 阶段多个角色并发各自开 agent 会话，若都写同一 repo，git 提交和验证器可能互相踩踏。

**为什么需要（边界场景）**：
- 4 个并行任务同时触发 rate limit → 4 个失败签名一起退避，重试窗口重叠，下一波又同时打进去（惊群）；
- 多角色并发时各自的 `git_commit` 在同一工作区交错提交，产物互相污染，验证器（如 `go build`）读到半成品状态误报失败；
- 换 agent 二进制时（`--agent-bin claude`）错误签名、会话标志、节流语义全变，当前无按供应商的配置分层。

**建议形态**：按 provider/model 的令牌桶限速 + 随机抖动（jitter）分散重试；并发任务默认独立 git worktree/branch，阶段结束后合并；`pi-batch.yaml` 中按 agent 二进制分层的会话标志与失败签名表。

---

## 4. 语义级产出验证（LLM-as-judge）与陈旧产出检测

**现状**：验证门是外部 shell 命令（exit code 语义），能查 `gofmt`/`go build`，但查不了"输出是否真的回答了任务"——agent 输出合规的 markdown 却答非所问时，当前机制会放行落盘。

**为什么需要（边界场景）**：
- meta 编排者输出合法 JSON 角色计划但角色与任务无关（内容空洞）；
- gate 阶段 VERDICT: PASS 行存在但理由为空/与交付物矛盾——`fail closed` 只防缺行，不防**假通过**；
- 单批任务产出的是"结构正确但结论陈旧"的文档（见方向 2 的指纹联动）。

**建议形态**：新增声明式校验器类型——结构化校验（输出必须含某标题/JSON schema）与 judge 校验（用一个便宜模型的独立会话按 rubric 打分，低于阈值拒绝落盘并触发重试），两者与现有 shell 验证器 AND 语义并存。这把"AI 产出是提案"从**制度声明**变成**强制门禁**。

---

## 5. 人机协同审批点（Human-in-the-loop Gate）与升级告警

**现状**：全自动链条直通 git commit + 归档 + 决策日志，无人工确认点；任务反复失败时只有 `--log-file` 被动记录，无人值守时"失败→重试→再失败"可以空转很久。

**为什么需要（边界场景）**：
- 归档/提交是不可逆操作（归档后工作区只剩决策日志），gate PASS 但内容有误时，自动提交把错误方案固化进 git 历史；
- 单任务连续失败 N 次（如供应商故障、prompt 系统性错误）时，继续轮循环纯烧钱——需要升级机制（停止 + 告警 + 保留现场）；
- 跨阶段交接（如设计→实现）前，人工确认可以省下整个下游的成本。

**建议形态**：pipeline 阶段级 `approval: true`（等待人工确认文件/命令，带超时自动拒绝），任务级 `max_failures` 升级策略（失败计数超限 → 停止轮循环、写决策日志、非零退出码供监控系统感知）。这是从"自动化工具"走向"可管控的 AI 研发流程"的产品分水岭。

---

**优先级建议**：1（成本熔断）和 2（状态机+指纹）是 7×24 无人值守的安全底座，应最先做；3 解决并行扩展的天花板；4、5 是把信任边界工程化的加分项。前两者不依赖供应商、纯自包含，风险最低、收益最直接。
