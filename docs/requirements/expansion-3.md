## 1. 成本与额度预算治理（Financial Circuit Breaker）

**现状**：系统对 quota / rate_limit / billing 只有**被动失败检测**（拒绝落盘 + 重试），但 7×24 无人值守、`--max-rounds 0` 无限轮循环、meta 编排并发多角色，这三个特性叠加会产生**无上限的 token 消耗**。没有任何一层知道"这个流水线/这个 24h 窗口已经花了多少钱、烧了多少 token"。

**为什么需要**：
- 无人值守的前提是"花钱有护栏"——一个失控的 meta 循环或错误的 `--max-rounds 0` 配置可以在一个周末烧掉整月预算，且失败签名检测救不了（每次调用都"成功"但低效）。
- 现有 `--min-interval` 只做时间节流，不做**预算节流**；`--retries` 指数退避是时间维度，缺成本维度。

**设计要点**：每次 agent 调用后从 CLI 输出/日志中解析 token 用量（或调用 provider API 对账）→ 写入累计计量文件 → 支持 per-batch / per-pipeline / 每日预算上限 → 超限自动**降级**（换更便宜模型或减少并发）或**熔断**（暂停轮循环，保留现场）。这是把"能跑"变成"可长期托管"的关键一步。

## 2. 任务状态持久化与结构化可观测性

**现状**：`--log-file` 是纯文本时间戳日志，决策日志是 markdown；断点续跑完全依赖"输出文件是否存在"（`--reuse`）这一隐式状态。7×24 场景下运营者无法回答：*哪些任务失败过、失败了几次、归因于哪类错误（quota vs 网络 vs 验证失败）、每任务耗时多少、当前这轮跑到哪了*。进程崩溃后，"进行中"的任务状态、重试计数、失败原因历史全部丢失。

**为什么需要**：
- 无人值守运维需要机器可消费的状态（systemd / Prometheus / 告警 webhook 都能读的 JSONL 事件流或 SQLite 状态库），而不是人肉 grep 日志。
- 失败归因聚合（quota 类占比 vs 验证失败占比）直接指导容量规划和重试策略调参；现在这些数据随进程消失。
- `--log-file` 无限追加，7×24 跑数月会爆盘——日志轮转本身就该有。

**设计要点**：每任务一个状态记录（pending/running/succeeded/failed/retried + 失败签名分类 + 耗时 + token 用量），原子写盘；`--resume` 从状态库恢复而非仅靠文件存在性；完成/失败时触发 webhook 通知（对接钉钉/邮件/ntfy）。这也为方向 1 的预算计量提供数据底座。

---

## 3. 内容寻址缓存：让 `--reuse` 不再"盲信存在性"

**现状**：`--reuse` 的判断标准是"输出文件存在即跳过"。但**输入变了输出没变**的情况完全无感知：prompt 模板改了、上游阶段产物变了、`from_dir` 目录里文档更新了、agent 二进制升级了——只要旧输出文件还在，就会被当作有效结果复用。在流水线场景中，上游变更后下游复用陈旧产物，等于**静默交付过期决策**，比失败更危险。

**为什么需要**：
- 这是 CI 领域早已解决的问题（cache key 语义）：复用必须基于"输入未变"而不是"产物存在"。
- 滚动分析（`for i in ...` 循环）场景下，每轮输出文件名带时间戳、天然不冲突，但 pipeline 的固定 `output` 路径会命中陈旧复用——目前唯一的规避手段是手动删文件，这不该是用户的责任。

**设计要点**：计算 cache key = hash(prompt 模板 + 上游产物内容 + 角色模板 + agent 版本 + 验证器配置)，key 未变才复用；同时**检测输出文件被并发/外部修改**（mtime 校验），解决并行任务写同一输出路径时"最后写入者胜"的竞态。附带收益：缓存命中可以跳过昂贵的 agent 调用，本身就是性能优化。

## 4. 上下文预算与记忆管理（Context Budget / Compaction）

**现状**：`--session-mode shared` 整个批次共用一个会话，meta 编排每轮"证据折叠"把前几轮结论全部喂给下一轮——两条路径都是**上下文无限增长**：token 成本线性上升，且 agent 在超长上下文中质量显著下降（指令遗忘、注意力稀释）。目前没有任何压缩、摘要或遗忘策略。

**为什么需要**：
- 这是当前架构中最确定的"长期运行必踩"问题：10 阶段 SDLC 评审 + 每阶段折叠证据，到第 8 阶段时上下文可能已经超出模型有效窗口，产出质量劣化但**系统不会报错**（失败签名检测抓不到"质量衰减"）。
- 与方向 1 联动：上下文膨胀是成本失控的头号来源，压缩即省钱。

**设计要点**：为共享会话设定上下文预算（如按 token 估算），超限时自动触发：摘要折叠（把早期阶段产出压缩为要点）→ 会话分叉/存档（fork 新会话只携带决策日志而非全文）→ 显式遗忘（仅保留 gate 裁决与决策点）。决策日志（2.8 节）已经是现成的"结构化记忆"雏形，可复用它作为压缩后的上下文载体。

---

## 5. 多 Agent 路由与全局限流协调

**现状**：切换 agent 靠配置（`agent.bin`），但一次运行内**只能用一个 bin**；每个任务的 model 可覆盖，却无法按任务特征路由（如摘要用便宜快模型、深度架构评审用强模型）；并行任务的限流是**各自为战**——10 个并发任务同时撞上 rate limit，各自退避 30s 后**同时重试再次撞车**，形成自我制造的限流风暴。

**为什么需要**：
- "成本-质量-延迟"三角只能在异构模型池上做权衡，单 bin 是硬约束。任务级 `model` 字段已有，缺的是路由策略层。
- 全局限流器（token bucket 按 provider 维度）让重试更智能：失败签名按"可重试性"分类，quota 类错误全局等待而非各自重试——这直接提升 7×24 场景的吞吐稳定性和方向 1 的预算可控性。

**设计要点**：任务声明式标注 `agent`/`model`/`tier`（cheap/standard/premium），调度器按 tier 路由；provider 级全局节流 + 故障降级（主 provider quota 耗尽时自动切备用 provider 或降 tier 重跑）；复用常驻 agent 进程减少每次调用的 CLI 启动开销（对短任务批次是实打实的性能收益）。

## 优先级建议

| 方向 | 风险等级 | 见效速度 | 建议 |
|---|---|---|---|
| 1 成本预算 | 高（财务失控） | 中 | **先做**——无人值守的前提 |
| 2 状态持久化 | 中（运维盲区） | 快 | 与 1 共享数据底座，一起做 |
| 4 上下文管理 | 高（质量劣化） | 中 | 长流水线必踩，紧随其后 |
| 3 内容寻址缓存 | 中（静默陈旧） | 快 | 独立小改动，可随时插入 |
| 5 多 Agent 路由 | 低（能力增强） | 慢 | 规划期预留接口即可 |

其中 1+2 共享"每次调用的结构化计量"这一基础设施，建议合并为一个里程碑落地；3 是纯增量且风险最低，可作为快速交付的试点。
